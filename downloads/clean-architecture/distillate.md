# Clean Architecture: A Craftsman's Guide to Software Structure and Design — Robert C. Martin

## Gist

Software is meant to be easy to change. Over time most systems get harder and harder to change, until each small change costs a fortune. This happens because the parts of the system are tangled together in the wrong way. The book's central model is this: separate the rules that make the business money from the tools and devices that serve those rules, and make every connection point from the tools toward the rules, never the other way. Then the tools can be swapped, delayed, or tested without touching the rules, and the system stays cheap to change for its whole life. With this model you can judge any software structure, decide where to draw lines between its parts, and choose how strongly to separate them.

## 1 Foundations: what architecture is for

### 1.1 Architecture and design

- **Architecture** is the set of significant design decisions that shape a system. A decision is significant in proportion to its cost of change.
- Time, money, and effort are the scale for telling architectural decisions from non-architectural ones, and for judging whether an architecture is good.
- **Design** and architecture are the same thing. There is no dividing line between high-level structure and low-level detail. They form one continuous fabric of decisions, from the highest level to the lowest. Example: an architect's drawings for a house show both the shape of the house and where every outlet, switch, and furnace goes.
- Boxes on a diagram are not the architecture. They are one chosen view, and every view is a choice of what to include and what to emphasize. Software architecture does not look like anything.
- Software is made of software: large components are built of smaller components, recursively. Physical scale does not apply to it, so building intuition does not transfer. Physical limits still matter: processor speed and network bandwidth judge performance, and memory and storage limit what a code base can do.
- The **rules of software architecture** are the same for every kind of system: embedded, batch, real-time, web, GUI, database, games, and so on. They are independent of every other variable. The reason is that all code, in any language and any paradigm, is still built from sequence, selection, iteration, and indirection, just as in the 1950s. The building blocks have not changed in 50 years, so the rules for ordering and assembling them have not changed either. Tools and hardware improved enormously (hardware power grew by at least 10^22 over the author's career); the essence of software did not.
- Believing that everything is new and the old rules no longer apply is a mistake. What has changed is knowledge: early programmers did not know the rules and broke them; after half a century they are now understood.

### 1.2 The goal and the measure

- **The goal of software architecture is to minimize the human resources required to build and maintain the required system.**
- **Design quality** is measured by the effort required to meet the customer's needs. If that effort is low and stays low for the life of the system, the design is good. If the effort grows with each release, the design is bad.
- A good architecture meets the needs of users, developers, and owners both at a given time and over time. The kinds of changes a system typically gets should not be the costly ones. They should fit into the daily and weekly flow of work, not need managed projects of their own.
- Bad architecture costs more than good architecture ("If you think good architecture is expensive, try bad architecture" — Foote and Yoder).
- Getting a program to work once is easy. Getting it right is hard. It takes knowledge, thought, discipline, and care for the craft. When software is right, it takes a fraction of the people to build and maintain, changes are simple and fast, and defects are few. When the structure is bad, everything is so tightly coupled that every trivial change takes weeks and carries high risk. Most developers fight through bad designs far more often than they work with good ones.

### 1.3 The signature of a mess

- The **signature of a mess**: staff grows each release, output flattens, and cost per line of code climbs. Example (real company): over 8 releases staff grew from about 20 to about 1200 developers while code grew from about 3000 KLOC to only about 7150 KLOC; cost per line was 40 times higher in release 8 than in release 1; monthly payroll went from a few hundred thousand dollars to $20 million, which bought almost nothing; productivity per release started near 100% and headed toward zero by release 4.
- These curves are unsustainable. However profitable the business is now, they drain profit and stall or collapse the company.
- A mess arises when a system is thrown together in a hurry, when headcount is the only driver of output, and when little thought goes to clean code or design structure.
- In a mess developers still work hard, but their effort goes into moving the mess around instead of into features. Left alone, the mess reduces productivity to zero in a matter of months.
- "We can clean it up later; we just have to get to market first" is false, because market pressure never lets up, so the cleanup never happens.
- Making messes is always slower than staying clean, at every time scale. The belief that messy code is faster in the short term is an error of fact, caused by overconfidence. Example: one developer solved the same kata on six days, with test-driven development (TDD) on alternate days; TDD days were about 10% faster, and the slowest TDD day beat the fastest non-TDD day. **The only way to go fast is to go well.**
- The fix for declining productivity is for developers to take responsibility for the mess, and for the organization to recognize its own overconfidence and take software architecture seriously. Starting over with a full redesign is not the answer, because the same overconfidence that made the first mess drives the redesign into the same mess. To take architecture seriously you must know which attributes of an architecture minimize effort.

### 1.4 Two values: behavior and structure

- Every software system gives its stakeholders two values: **behavior** and structure (architecture). Developers are responsible for keeping both high. Developers often focus on one, often the lesser one, and the system ends up with no value.
- Behavior is making the machine do what makes or saves money for stakeholders: helping write the requirements, writing code that meets them, and fixing bugs. Believing this is the programmer's whole job is a mistake.
- Software was invented to be "soft": an easy way to change machine behavior. If it is not easy to change, it might as well be hardware. The clean approach treats this softness as a first-class property and preserves it.
- The difficulty of a change should be proportional only to its **scope**, not to its **shape**. Costs grow out of proportion to the size of requests when the system's shape does not match the shape of the requests: each new change is a jigsaw piece forced into a puzzle of growing complexity. So architectures should be as shape-agnostic as practical, because the more an architecture prefers one shape, the harder new features become to fit.
- Architecture (ease of change) is the greater value. Proof from extremes: a program that works perfectly but cannot be changed becomes useless when requirements change; a program that does not work but is easy to change can be made to work and kept working. No program is literally impossible to change, but a system is practically impossible to change when the cost of a change exceeds its benefit. Many systems reach that point in some features.
- Managers say they value changeability but rank current features higher. Yet they are furious when a needed change turns out unaffordable.
- **Eisenhower matrix**: the urgent is rarely important and the important is seldom urgent. Behavior is urgent but not always important. Architecture is important but never particularly urgent. Priority order: (1) urgent and important, (2) important not urgent, (3) urgent not important, (4) neither. Architecture sits in 1 and 2; behavior sits in 1 and 3. The common mistake is raising items from position 3 to position 1, which sacrifices the important architecture for unimportant features.
- Business managers cannot judge the importance of architecture; developers are hired for that. So the development team must assert the importance of architecture over the urgency of features, arguing with other stakeholders as equals. Fighting for architecture is always a struggle among stakeholders. The **software architect** focuses more on structure than features, so this duty weighs double on them. If architecture comes last, the system grows ever more costly and finally becomes practically impossible to change; that means the team did not fight hard enough.

### 1.5 Two ways architecture fails

- Seeking stability through authority and rigidity, by forbidding change because change is expensive, makes the architect a dictator and the architecture a constant frustration.
- **Speculative generality** — guesswork hard-coded in advance, countless parameters, dead code, excess accidental complexity — burdens the maintenance budget.
- Architecture must be decided with incomplete knowledge, because shaping decisions around future changes requires predicting the future. Architecture is a hypothesis to be proven by implementation and measurement. Good architecture is an ongoing process of inquiry and experiment, not a frozen artifact.

## 2 The bricks: programming paradigms

### 2.1 What a paradigm is

- A **programming paradigm** is a way of programming, mostly unrelated to language, that tells you which structures to use and when. There are three: structured, object-oriented, and functional programming. There are unlikely to be others.
- Each paradigm removes a capability and adds none. Each is a negative discipline: it says what not to do.
  - **Structured programming** imposes discipline on direct transfer of control (it removes goto).
  - **Object-oriented programming (OO)** imposes discipline on indirect transfer of control (it removes raw function pointers).
  - **Functional programming** imposes discipline on assignment (it removes unrestricted assignment).

- Together they remove goto, function pointers, and assignment. There is probably nothing left to remove. Evidence: all three were found between 1958 and 1968 (lambda calculus itself dates from 1936), and none has been added since. Functional was invented first, structured adopted first (Dijkstra, 1968), OO discovered in 1966 (Dahl and Nygaard).
- Software architecture begins with the code.

### 2.2 Structured programming

- Programming is hard: any program of real complexity has too many details for a human to manage unaided, and one overlooked detail makes a program that seems to work but fails in surprising ways.
- Dijkstra wanted to apply mathematical proof to programs, building a hierarchy of proven structures. He found that certain uses of goto prevent a module from being split recursively into smaller units, which blocks the divide-and-conquer needed for proofs. Uses of goto that match simple selection (if/then/else) and iteration (do/while) do not have this problem.
- Böhm and Jacopini proved that every program can be built from three structures: sequence, selection, and iteration. These are exactly the structures that make modules provable. This coincidence gave birth to structured programming.
- Proof method for structured code: prove sequences by enumeration (trace inputs to outputs); prove selection by enumerating each path; prove iteration by induction (prove case 1, prove that N implies N+1, prove start and end criteria).
- Dijkstra's 1968 letter "Go To Statement Considered Harmful" won the argument: goto has nearly vanished from modern languages. Everyone is a structured programmer now because languages no longer allow undisciplined direct transfer of control. Java named breaks and exceptions are not harmful gotos; they are not unrestricted, and languages that keep goto usually limit its target to the current function.
- **Functional decomposition**: because structured code can be decomposed recursively into provable units, a large problem can be broken into high-level functions, then lower-level functions, without limit. Structured analysis and structured design (popular late 1970s–1980s) were built on it.
- The dream of formal proofs failed. The hierarchy of theorems was never built, and few programmers think formal proofs are the way to quality.
- Mathematics proves statements true. Science proves statements false. A scientific law is falsifiable but not provable; we trust it after failing to disprove it. Not every statement is provable.
- **Testing shows the presence, not the absence, of bugs.** A test can show a program incorrect but cannot show it correct; after enough testing we deem it correct enough. So software development is like a science, not like mathematics.
- Testing can only falsify a provable program. A program that is not provable (for example, because of unrestrained goto) can never be deemed correct, however many tests it passes.
- So structured programming's lasting value is that it creates **falsifiable** (testable) units: it forces decomposition into small provable functions, and tests then try to show them incorrect. This is why languages dropped unrestrained goto and why functional decomposition is still a best practice at the architectural level. At every level, from function to component, software is driven by falsifiability: architects define modules, components, and services that are easy to falsify, using restrictive disciplines like structured programming at a higher level.

### 2.3 Object-oriented programming

- The basis of good architecture is understanding and applying object-oriented design.
- Origin: Dahl and Nygaard saw that an ALGOL function's stack frame could be moved to a heap, so its local variables outlived the call. The function became a class constructor, its local variables instance variables, and its nested functions methods. This led to polymorphism through disciplined use of function pointers.
- "OO is the combination of data and function" is a poor definition: it implies o.f() differs from f(o). "OO models the real world" is too vague to say anything. The usual definition — encapsulation plus inheritance plus polymorphism — does not hold up either.
- **Encapsulation** is drawing a line around a cohesive set of data and functions so that outside the line the data is hidden and only some functions are known. OO earns no credit for it. C had perfect encapsulation: a header declared a struct and its functions, the struct's members lived only in the implementation file, and users knew nothing of them. C++ broke this because the compiler must know instance sizes, so members must appear in the header; clients then see them and must recompile when they change. public/private/protected only partly repair this. Java and C# went further and removed the header/implementation split entirely. Many OO languages (Smalltalk, Python, JavaScript, Lua, Ruby) enforce little or no encapsulation; they rely on programmers behaving well. OO languages have weakened the encapsulation C had.
- **Inheritance** is the redeclaration of a group of variables and functions within an enclosing scope. C programmers did it by hand: a struct whose leading fields match another struct's could be cast and passed as that struct. C++ implements single inheritance this way. The manual trick is less convenient (explicit casts) and makes multiple inheritance hard. OO earns perhaps half credit: it made this much more convenient but did not invent it.
- **Polymorphism** is an application of pointers to functions. Example: UNIX requires each IO driver to provide open, close, read, write, and seek with identical signatures; a FILE structure holds pointers to them, and getchar() calls STDIN->read(). So a copy program built on getchar/putchar behaves differently depending on the device behind STDIN and STDOUT. C++ does the same with a vtable of virtual-function pointers.
- Raw function pointers are dangerous: polymorphism built on them depends on manual conventions (initialize the pointers; call everything through them), and one forgotten convention makes a bug that is very hard to find. OO removes those conventions and makes polymorphism safe, convenient, and trivial. This is OO's real contribution, and the sense in which it disciplines indirect transfer of control.
- With polymorphism, adding a new IO device needs no change and no recompile of the copy program, because the copy program's source code depends only on the FILE interface, not on the drivers. The devices are **plugins**.
- **Device independence** is the property that a program does not depend on the specific IO device it uses. The industry learned its value in the late 1950s: programs written for card decks had to be largely rewritten when customers moved to magnetic tape, though the job was the same. So operating systems made IO devices plugins. Most programmers did not use this **plugin architecture** in their own programs, because function pointers were dangerous. OO lets the plugin architecture be used anywhere, for anything.
- A **source code dependency** exists when one module's source code names another module (#include, import, using). Without safe polymorphism, source code dependencies follow the **flow of control**: in a call tree main → high-level → mid-level → low-level, each caller must name the callee's module. Behavior dictates flow, and flow dictates dependencies; the architect has no choice.
- **Dependency inversion**: if a high-level module calls F() through an interface I, and the low-level module implements I, the source code dependency points against the flow of control. At runtime the interface does not exist; the caller just calls F() indirectly. Because OO makes polymorphism safe, any source code dependency can be inverted by inserting an interface. So in an OO system the architect has absolute control over the direction of every source code dependency, independent of the flow of control.
- Example: invert dependencies so the database and the UI depend on the **business rules** (the code that makes or saves the business money), not the reverse. Then the UI and database are plugins to the business rules, and the business-rule source code never mentions them.
- If the business rules, UI, and database are compiled into separate **components** (deployment units such as jar files, DLLs, or Gem files) with the same dependencies as the source code, the business-rules component does not depend on the others. It can be deployed alone, and UI or database changes do not affect it. **Independent deployability**: when a component's source changes, only that component is redeployed. **Independent developability**: modules that deploy independently can be developed independently by different teams.
- Working definitions [bridging]: **policy** is the business rules and procedures, where the system's value lives; **details** are the IO devices, databases, frameworks, and other mechanisms through which the policy talks to the outside world.
- **To the architect, OO is the ability, through polymorphism, to gain absolute control over every source code dependency, so that modules holding high-level policies are independent of modules holding low-level details, and the details become plugins developed and deployed independently.**

### 2.4 Functional programming

- In functional languages variables do not vary. Example: printing the first 25 squares in Clojure composes range (a lazy, never-ending list), map, take, and println, with no variable ever modified; a lazy list is safe because no element exists until it is accessed.
- All race conditions, deadlocks, and concurrent update problems come from mutable variables. With no updates, there are no races or concurrent updates; with no mutable locks, no deadlocks. Architects must make systems robust under multiple threads and processors, so immutability matters to them.
- Full immutability is practical only with infinite storage and processor speed. Otherwise it needs compromises.
- **Segregation of mutability**: split the application (or its services) into immutable components that work purely functionally and mutable components that allow state change; the immutable ones talk to the mutable ones. Protect the mutable state from concurrent updates with some kind of **transactional memory**, which guards variables in memory the way a database guards records, with a transaction or retry scheme.
- Example: a Clojure atom changes only through swap!, which uses compare-and-swap: (1) read the current value and pass it to the update function; (2) when it returns, lock the variable and compare its value to the value passed in; (3) if equal, store the new value and unlock; (4) otherwise unlock and retry from step 1. An atom is enough for simple cases but does not protect against concurrent updates and deadlocks when several dependent variables are involved; those need more elaborate facilities.
- Push as much processing as possible into the immutable components, and drive as much code as possible out of the components that must allow mutation.
- The more memory and speed machines have, the less mutable state is needed.
- **Event sourcing** stores the transactions, not the state; when state is needed, all transactions from the beginning of time are applied. Example: a bank stores deposits and withdrawals and computes a balance by summing them, with no mutable balance. Storage grows without bound, but it only needs to work for the reasonable lifetime of the application, and storage is now huge. Shortcut: save a snapshot of the state periodically (for example, every midnight) and apply only transactions since the snapshot. Nothing is ever updated or deleted, so the application is CR instead of CRUD and has no concurrent update problems. Source code control systems work exactly this way. With enough storage and processing power, an application can be entirely immutable and entirely functional.
- What half a century has taught is what not to do.

### 2.5 How the paradigms map onto architecture

- The three paradigms match the three big concerns of architecture: function, separation of components, and data management. Structured programming is the algorithmic foundation of modules. Polymorphism (from OO) is the mechanism for crossing the boundaries between components. Functional programming disciplines where data lives and how it is accessed.

## 3 Module-level design: the SOLID principles

### 3.1 Purpose and scope

- Good systems start with clean code, but clean code is not enough: a large mess can be made from well-made bricks. The **SOLID principles** say how to arrange functions and data structures into classes and how to connect those classes.
- Here a **class** is any coupled grouping of functions and data. Every system has such groupings, so SOLID is not limited to OO.
- Goal: mid-level structures that tolerate change, are easy to understand, and can be the basis of components used in many systems. "**Mid-level**" means they are applied at the module level, just above the code.
- A system-wide mess can still be made from well-designed mid-level parts, so SOLID must be followed by component principles and then high-level architecture principles.
- A **module**, most simply, is a source file. Where code is not kept in files, a module is a cohesive set of functions and data structures.
- Diagram notation used below: <I> marks an interface, <DS> a data structure. An arrow from A to B (a **source code dependency**) means A's source code mentions B's name and B mentions nothing of A.

### 3.2 SRP: the Single Responsibility Principle

- **SRP: a module should be responsible to one, and only one, actor.** An **actor** is a group of one or more people who require the same kind of change to the system. (The older wording, "a module should have one, and only one, reason to change," means the same: the reasons are the users and stakeholders the system changes to satisfy.)
- The SRP does not mean "every module should do one thing." That is a different, real principle for functions, used when refactoring large functions into small ones; it is not the SRP and not part of SOLID. The SRP is probably the least understood SOLID principle because its name suggests the wrong meaning.
- **Cohesion** is the force that binds together the code responsible to a single actor.
- The SRP is an active corollary of **Conway's law**: a system's best structure is heavily shaped by the social structure of the organization that uses it.
- Its violations show two symptoms.
  - **Accidental duplication.** Example: an Employee class has calculatePay() (specified by accounting, reporting to the CFO), reportHours() (by HR, reporting to the COO), and save() (by DBAs, reporting to the CTO). The first two share a regularHours() function. The CFO's team asks for a tweak; a developer changes regularHours(), not seeing that reportHours() also calls it; the CFO's team validates it; HR's reports silently go wrong, costing millions. This happens because code that different actors depend on sits close together. Careful developers who avoid duplication cause it: factoring an algorithm two actors share into one function couples the actors, though their needs may later diverge.
  - **Merges.** Files with many methods responsible to different actors get frequent merges, as when a DBA schema change and an HR report-format change hit the same file. Merges are always risky; no tool handles every case, and a merge of changes from different actors puts all of them at risk.
- Every SRP symptom is several people changing one source file for different reasons. The cure is always to separate the code that supports different actors.
- Solutions (all move functions into different classes):
  1. Put the data in a plain data structure with no methods (EmployeeData). Put each actor's functions in its own class (PayCalculator, HourReporter, EmployeeSaver). The classes share the data but must not know about each other. To avoid tracking several classes, add a **Facade**: a class with very little code that creates the classes and delegates to them.
  2. To keep the most important business rules near the data, keep the most important method (calculatePay) in the Employee class and let that class be the Facade for the lesser functions.
- Separated classes are not one-function classes. Each job needs many functions, so each class has many private methods. Each such class is a **scope**: outside it, no one knows its private members exist.
- The SRP reappears at higher levels: as a principle for grouping classes into components, and as the rule for where to draw architectural boundaries.

### 3.3 OCP: the Open-Closed Principle

- **OCP: a software artifact should be open for extension but closed for modification.** Its behavior should be extendable without modifying it, so that behavior changes by adding new code rather than changing old code.
- The OCP is the most fundamental reason to study software architecture. If simple extensions to the requirements force massive changes to the software, the architects have failed spectacularly. It matters even more for components than for classes.
- A good architecture cuts the old code changed for a new feature to the barest minimum, ideally zero.
- Method: (1) separate the things that change for different reasons (SRP); (2) organize the dependencies between them so they point the right way, grouping classes into components so dependencies cross each component boundary in one direction.
- Example: a financial summary shown on a web page (negatives in red) must also be printed as a paginated black-and-white report (negatives in parentheses). Two responsibilities: computing the reportable data, and presenting it (web and print). Components: Controller (FinancialReportController, FinancialReportPresenter <I>); Interactor (FinancialReportGenerator, FinancialReportRequester <I>, FinancialReportRequest <DS>, FinancialReportResponse <DS>, FinancialDataGateway <I>, FinancialEntities); Database (FinancialDataMapper, FinancialDatabase); Screen Presenter and Print Presenter (presenters, view models <DS>, view interfaces <I>); Web View and PDF View (implement the view interfaces).
- Cross each component boundary in one direction only. Arrows point toward the components to be protected. **If component A should be protected from changes in component B, B should depend on A.**
- In the example, the Controller is protected from the Presenters, the Presenters from the Views, and the Interactor from everything. The Interactor holds the most protected position because it contains the business rules, the highest-level policies; everything else is peripheral. Centrality is relative: the Controller is peripheral to the Interactor but central to the Presenters and Views.
- Protection forms a hierarchy by **level**. Working definition (made precise later): the higher the level, the more central the policy and the farther it is from the system's inputs and outputs. The highest-level components are the most protected and the lowest-level the least.
- **How the OCP works architecturally:** separate functionality by how, why, and when it changes, then arrange it in a hierarchy of components where higher-level components are protected from changes to lower-level ones.
- Much of the apparent complexity of an OCP design exists for two purposes:
  - **Directional control**: the FinancialDataGateway interface inverts the dependency that would otherwise run from the Interactor to the Database; the Presenter and View interfaces do the same.
  - **Information hiding**: the FinancialReportRequester interface keeps the Controller from knowing the Interactor's internals; without it the Controller would have **transitive dependencies** on FinancialEntities. Software entities should not depend on things they do not directly use. The first priority is protecting the Interactor from the Controller, but the Controller is also protected from the Interactor by hiding the Interactor behind an interface.

### 3.4 LSP: the Liskov Substitution Principle

- **LSP** (Liskov, 1988): S is a **subtype** of T if, for every program P written in terms of T, P's behavior is unchanged when an S object is substituted for a T object. In short: to build from interchangeable parts, the parts must keep a contract that lets one replace another.
- Example that conforms: Billing calls calcFee() on License; PersonalLicense and BusinessLicense use different algorithms, but Billing's behavior does not depend on which it gets.
- Example that violates (the **square/rectangle problem**): a Rectangle's height and width change independently, a Square's must change together. Code that sets width 5 and height 2 and expects area 10 fails on a Square. The only defense is code in the user that detects the real type (an if); then the user depends on the types, so they are not substitutable.
- The LSP began as a guide to inheritance. It is now a broader principle about interfaces and implementations of any form: a Java interface with several implementations, Ruby classes sharing method signatures, or services that answer the same REST interface.
- Example (architecture): a taxi aggregator stores each company's dispatch URI and sends a PUT to URI/pickupAddress/…/pickupTime/…/destination/…, so every company's service must accept the same REST interface. One company abbreviates "destination" to "dest".
  - Never handle this with a hard-coded special case such as `if (driver.getDispatchUri().startsWith("acme.com"))`. A company name in code invites horrible, mysterious errors and security breaches, and the special cases multiply as the business changes.
  - Instead, isolate the difference: a dispatch-command creation module driven by a configuration database keyed by URI pattern, mapping each pattern to its dispatch format.
- One violation of substitutability can pollute an architecture with much extra, complex mechanism. So the LSP can and should be extended to the level of architecture.

### 3.5 ISP: the Interface Segregation Principle

- **ISP: avoid depending on things you do not use.**
- Example: User1, User2, and User3 each use only op1, op2, or op3 of one OPS class. In Java, User1's source code still depends on op2 and op3, so a change to op2 forces User1 to be recompiled and redeployed though nothing it uses changed. Fix: split the operations into interfaces (U1Ops, U2Ops, U3Ops) that OPS implements; each user depends only on its own interface.
- This is a static-typing effect: statically typed languages force declarations that users import or include, and those create source code dependencies. In dynamically typed languages (Ruby, Python) declarations are inferred at runtime, so these dependencies do not exist. This is the primary reason dynamically typed languages make systems more flexible and less tightly coupled.
- The ISP is still an architecture issue, not just a language issue: at any level, depending on modules that contain more than you need is harmful. Example: system S uses framework F, which is bound to database D. Changes to features of D that F and S do not use may force F and S to be redeployed, and a failure in those features may make F and S fail. Depending on baggage you do not need causes trouble you did not expect.

### 3.6 DIP: the Dependency Inversion Principle

- **DIP: the most flexible systems are those in which source code dependencies refer only to abstractions, not to concretions.** Code that implements high-level policy should not depend on code that implements low-level details; details should depend on policies.
- In a statically typed language, use/import/include statements should refer only to modules holding interfaces, abstract classes, or other abstract declarations. In a dynamically typed language the rule is the same; a **concrete module** there is any module in which the called functions are implemented.
- The DIP is not absolute. Systems must depend on many concrete facilities, such as Java's String class, and should. Dependencies on concrete but very stable things (the operating system and platform) are tolerated because they change rarely and under tight control. The targets of the DIP are the **volatile** concrete elements: modules under active development that change often.
- Interfaces are less volatile than implementations: every change to an interface forces changes to its implementations, but changes to implementations usually do not force changes to interfaces. Good designers work hard to reduce interface volatility, adding functionality to implementations without changing interfaces. Stable architectures avoid depending on volatile concretions and favor stable abstract interfaces.
- Coding practices:
  1. Do not refer to volatile concrete classes; refer to abstract interfaces. This holds in all languages, constrains object creation severely, and usually requires Abstract Factories.
  2. Do not derive from volatile concrete classes. In static languages inheritance is the strongest, most rigid source code relationship; use it with great care. In dynamic languages it is still a dependency, so caution is always wise.
  3. Do not override concrete functions. Concrete functions often carry source code dependencies, and overriding inherits them. Make the function abstract and write several implementations.
  4. Never mention the name of anything concrete and volatile.
- Creating an object requires a source code dependency on its concrete definition in virtually every language. An **Abstract Factory** manages this: the Application uses ConcreteImpl through a Service interface and gets instances by calling makeSvc() on a ServiceFactory interface; ServiceFactoryImpl implements it, creates ConcreteImpl, and returns it as a Service.
- In that structure an **architectural boundary** separates the abstract from the concrete, and every source code dependency crosses it toward the abstract side. The abstract side holds the high-level business rules; the concrete side holds the details they manipulate. The flow of control crosses the boundary opposite to the source code dependencies; this inversion gives the principle its name.
- DIP violations cannot be removed entirely (the concrete factory depends on a concretion), but they can be gathered into a few concrete components kept apart from the rest. Most systems have at least one, often called **main** because it holds the main function. Example: main creates ServiceFactoryImpl and puts it in a global variable of type ServiceFactory, which the Application uses.
- The abstract/concrete boundary becomes the system's architectural boundaries. The rule that source code dependencies cross such a boundary only toward the more abstract, higher-level side is the **Dependency Rule**.

## 4 Components

### 4.1 What a component is

- SOLID arranges bricks into walls and rooms; the component principles arrange rooms into buildings.
- A **component** is a unit of deployment: the smallest entity that can be deployed as part of a system. Examples: jar files (Java), gems (Ruby), DLLs (.Net). In compiled languages it is an aggregation of binary files; in interpreted languages, of source files. Components can be linked into one executable, bundled into one archive (such as a .war file), or deployed separately as dynamically loaded plugins (.jar, .dll, .exe).
- However they are finally deployed, well-designed components always keep the ability to be deployed independently, and therefore developed independently.
- Today's components are dynamically linked files plugged together at runtime. History: early programs were loaded at fixed addresses and libraries were compiled in as source, which made compiles take hours; libraries were then compiled separately and loaded at fixed addresses, which fragmented memory as programs grew; relocatable binaries and linking loaders fixed that (a **linking loader** matches each called function, an external reference, to its external definition); as programs grew, linking was split from loading because it took over an hour; by the mid-1990s faster hardware made linking at load time take seconds again. **Murphy's law of program size**: programs grow to fill all available compile and link time. Moore's law (speed, memory, and density double every 18 months) held from the 1950s to 2000, then stopped for clock rates; in the late 1980s it beat Murphy's law. The result is the **component plugin architecture** (for example, .jar files in a mods folder, or DLLs loaded into an IDE). After 50 years, a component plugin architecture can be the casual default instead of a herculean effort.

### 4.2 Component cohesion: which classes go in which component

- Deciding which classes belong in which component is an important decision that has usually been made ad hoc. Three principles guide it: REP, CCP, CRP.
- **REP — Reuse/Release Equivalence Principle: the granule of reuse is the granule of release.** People cannot and will not reuse components unless the components are tracked through a release process and given release numbers, because without numbers there is no way to make reused components compatible, and users need to know when releases come and what they change. The release process must produce notices and documentation so users can decide when, and whether, to integrate a new release; users often keep the old one. So the classes in a component must share an overarching theme or purpose, and must be releasable together: one version number, one release tracking, and one set of release documentation must make sense to both author and users. REP's advice ("make sense") is weak, but violations are easy to spot because they do not make sense to users. CCP and CRP define REP more strongly, in a negative sense.
- **CCP — Common Closure Principle: gather into components the classes that change for the same reasons and at the same times; separate into different components the classes that change at different times and for different reasons.**
  - CCP is the SRP for components: SRP separates methods into classes by reason to change; CCP separates classes into components.
  - For most applications maintainability matters more than reusability. If a change is confined to one component, only that component is redeployed, and components that do not depend on it need no revalidation or redeployment. So it is better for a change to touch one component than many. Classes so tightly bound, physically or conceptually, that they always change together belong in the same component.
  - CCP relates to the closure of the OCP. Complete closure is impossible, so closure is strategic: design classes closed to the most common kinds of change expected or experienced, and put classes closed to the same kinds of change in the same component, so that a requirement change is likely to touch as few components as possible.
  - SRP and CCP together: **gather together the things that change at the same times and for the same reasons; separate the things that change at different times or for different reasons.**
- **CRP — Common Reuse Principle: do not force users of a component to depend on things they do not need.** Classes that tend to be reused together belong in the same component.
  - Classes are seldom reused alone; reusable classes collaborate with others in the same abstraction, so a component typically holds classes with many dependencies on each other. Example: a container class and its iterators.
  - Depending on a component means depending on all of it, even if you use one class. When it changes, the user likely must change, or at least be recompiled, revalidated, and redeployed, even if it does not care about the change. So the classes in a component should be inseparable: it should be impossible to depend on some and not the others. Otherwise more components are redeployed than necessary.
  - CRP says more about which classes should not be together: classes not tightly bound to each other should not share a component.
  - CRP is the general form of the ISP: ISP says do not depend on classes with methods you do not use; CRP says do not depend on components with classes you do not use. Both say: **do not depend on things you do not need.**

### 4.3 The cohesion tension

- The three principles fight each other. REP and CCP are inclusive: they make components larger. CRP is exclusive: it makes components smaller.
- **Tension diagram**: a triangle with REP ("group for reusers"), CCP ("group for maintenance"), and CRP ("split to avoid unneeded releases") at the corners. Each edge names the cost of abandoning the opposite corner:

  | Edge | Principle abandoned | Cost |
  |---|---|---|
  | REP–CCP | CRP | too many unneeded releases |
  | REP–CRP | CCP | too many components change |
  | CCP–CRP | REP | hard to reuse |

- Focusing only on REP and CRP makes simple changes touch too many components. Focusing too strongly on CCP and REP generates too many unneeded releases.
- A good architect picks the position in the triangle that meets the team's current concerns, knowing those concerns change over time. Early in a project, CCP is much more important than REP, because developability matters more than reuse. Projects generally start at the CCP–CRP edge, sacrificing only reuse, and slide toward REP as they mature and other projects draw on them. So component structure depends more on how the project is developed and used than on what it does. The right partition is almost always dynamic; today's may be wrong next year, and composition will jitter and evolve.
- The old view of cohesion was "a module performs one function." The three principles describe a richer cohesion of opposing forces: reusability against developability.

### 4.4 Component coupling: ADP

- The coupling principles (ADP, SDP, SAP) govern relationships between components. The forces on component structure are technical, political, and volatile.
- **ADP — Acyclic Dependencies Principle: allow no cycles in the component dependency graph.**
- The problem it solves is the **morning after syndrome**: you get something working, and the next morning it no longer works because someone changed something you depend on. It arises when many developers modify the same source files. It is minor in small projects and nightmarish in large ones, where weeks can pass without a stable build.
- One old fix is the **weekly build**: everyone works privately for four days and integrates on Friday. As the project grows, integration spills into Saturday and then starts midweek, efficiency drops, the build becomes biweekly, and integration keeps growing. Lengthening the schedule raises risk, makes integration and testing harder, and loses fast feedback.
- The better fix:
  1. Partition the development environment into releasable components, each owned by one developer or team.
  2. When a component works, release it with a release number into a directory other teams use.
  3. Keep developing it privately; everyone else uses the released version.
  4. Each team decides when to adopt a new release of the components it uses, or keeps the old one.
  This means no team is at the mercy of another, and integration happens in small increments with no all-hands integration point. It works only if the component dependency graph has no cycles. With cycles, the morning after syndrome cannot be avoided.
- The component dependency structure is a directed graph. If from any component you can never follow dependencies back to it, the graph is a **directed acyclic graph (DAG)**. Example DAG: Main depends on View, Controllers, Authorizer, Interactors, Database; View depends on Presenters; Presenters, Controllers, Authorizer, and Database depend on Interactors; Interactors and Database depend on Entities.
- In a DAG:
  - To see who is affected by a new release of a component, follow the arrows backward. A component with no dependents (Main) affects no one when released.
  - To test a component, build it only with the versions of the components it depends on.
  - To release the whole system, go bottom-up: release the components with no dependencies first (Entities), then their dependents (Database, Interactors), and so on, with Main last.
- Example cycle: a new requirement makes User in Entities use Permissions in Authorizer, giving Entities → Authorizer → Interactors → Entities.
- A cycle makes its components effectively one large component. All their developers suffer the morning after syndrome because they must use exactly the same release of each other's components, other components must be compatible with all of them, and testing one requires building and integrating the others. Unit testing and releasing become hard and error-prone. Build problems grow geometrically with the number of modules. The build order becomes hard or impossible to determine, which causes nasty problems in languages like Java that read declarations from compiled binaries. Clue: if a simple unit test of one class needs many libraries and much of everyone else's code, there are probably cycles.
- **A cycle can always be broken.** Two ways:
  1. Apply the DIP: put an interface holding the methods the depending class needs (what User needs) in the depending component (Entities), and make the other component (Authorizer) implement it.
  2. Create a new component that both depend on, and move into it the classes both need.
- The second way shows that component structure is volatile: it jitters and grows as requirements change. It must always be monitored for cycles, which must be broken when they appear, sometimes by creating new components.

### 4.5 Components are not designed top-down

- Component structure cannot be designed top-down. It is not one of the first things designed; it evolves as the system grows.
- A component dependency diagram is not a functional decomposition and says little about what the application does. It is a map of the application's buildability and maintainability. That is why it is not designed at the start: there is nothing yet to build or maintain.
- How it evolves: as modules accumulate, SRP and CCP group classes that change together; as reusable elements appear, CRP comes in; as cycles appear, ADP is applied and the graph jitters and grows. Designing the component structure before any classes would likely fail badly: little would be known about common closure, reusable elements would be unknown, and cycles would almost certainly appear.
- An overriding concern is isolating volatility. Components that change often and capriciously must not affect components that should be stable. Example: cosmetic GUI changes must not affect business rules; report changes must not affect the highest-level policies. Architects shape the graph to protect stable, high-value components from volatile ones.

### 4.6 SDP: the Stable Dependencies Principle

- **SDP: depend in the direction of stability.**
- Designs cannot be static. CCP creates components that are sensitive to some changes and immune to others, and some components are meant to be volatile. A component meant to be volatile must not be depended on by a component that is hard to change, or it becomes hard to change too. A module designed to be easy to change can be made hard to change by someone hanging a dependency on it, without a line of its code changing.
- **Stability** means "not easily moved": the amount of work needed to make a change, not how often it changes. A penny on its edge is unstable though it may not move for years; a table is stable. Size, complexity, and clarity also affect stability, but the sure way to make a component hard to change is to have many components depend on it, because every change must be reconciled with all dependents.
- A component others depend on is **responsible** to them. A component that depends on nothing is **independent**. Responsible and independent means stable. A component nothing depends on is **irresponsible**; one that depends on others is **dependent**. Irresponsible and dependent means unstable.
- Metrics:
  - **Fan-in**: number of classes outside the component that depend on classes inside it (incoming dependencies; formerly called afferent couplings, Ca).
  - **Fan-out**: number of classes inside the component that depend on classes outside it (outgoing dependencies; formerly efferent couplings, Ce).
  - **Instability I = Fan-out / (Fan-in + Fan-out)**, range 0 to 1. I = 0 is maximally stable: Fan-in > 0 and Fan-out = 0, so dependents make it hard to change and nothing forces it to change. I = 1 is maximally unstable: Fan-in = 0 and Fan-out > 0, so nothing restrains change and its dependencies may force change.
  - Example: 3 outside classes depend on component Cc and Cc depends on 1 outside class: I = 1/(3+1) = 1/4.
  - Counting: in C++ count #include statements (easiest with one class per source file); in Java count import statements and qualified names.
- **SDP in metric form: a component's I should be larger than the I of the components it depends on. I decreases in the direction of dependency.**
- Not every component should be stable; if all were maximally stable the system could not change. The ideal: changeable components at the top depend on stable components at the bottom. Draw unstable components at the top; then any arrow pointing up violates the SDP (and the ADP).
- Example violation and fix: a developer in component Stable makes class U depend on class C in Flexible, a component meant to be easy to change; now Flexible cannot change without affecting Stable and all its dependents. Fix with the DIP: create an interface US declaring the methods U needs, put it in a new component UServer, and make C implement it. Stable and Flexible both depend on UServer (I = 0); Flexible keeps I = 1; all dependencies run toward decreasing I.
- An **abstract component** contains only interfaces and no executable code. It is very stable, an ideal target for less stable components, and a common, necessary tactic in statically typed languages (Java, C#). In dynamically typed languages (Ruby, Python) abstract components do not exist, and dependency structures are simpler, because inverting a dependency needs no declared or inherited interface.

### 4.7 SAP: the Stable Abstractions Principle

- **SAP: a component should be as abstract as it is stable.**
- High-level architecture and policy decisions should not change often, so they belong in stable components (I = 0). Unstable components (I = 1) should hold only volatile code meant to change quickly. But stable code is hard to change, which could make the architecture inflexible. The OCP resolves this: abstract classes can be extended without modification. So a stable component should be abstract, so its stability does not block extension, and an unstable component should be concrete, so its code is easy to change. Stable components made of interfaces and abstract classes are flexible and do not overly constrain the architecture.
- SDP plus SAP is the DIP for components: dependencies run toward stability, stability implies abstraction, so dependencies run toward abstraction. Difference: a class is either abstract or not, while a component can be partly abstract and partly stable.
- **Abstractness A = Na / Nc**, where Nc is the number of classes in the component and Na the number of abstract classes and interfaces. A = 0: no abstract classes. A = 1: only abstract classes.
- The **I/A graph** plots A (vertical) against I (horizontal). The ideal components sit at (0, 1), maximally stable and abstract, and (1, 0), maximally unstable and concrete. Most components lie between; for example, an abstract class derived from another abstract class is maximally abstract but, having a dependency, not maximally stable. So the reasonable positions are found by excluding bad zones:
  - **Zone of Pain**, around (0, 0): stable and concrete. Such components are rigid: they cannot be extended (not abstract) and are hard to change (stable). Well-designed components are not normally there. Example: a database schema is volatile, extremely concrete, and heavily depended on, which is one reason the boundary between OO code and databases is hard to manage and schema updates are painful. A concrete utility library such as String also sits near (0, 0) but is nonvolatile: so many things use it that changing it would cause chaos, so it does not change. (The book also says such a library "has an I metric of 1," which conflicts with its position near (0, 0); the position implies I near 0.) Nonvolatile components are harmless in the Zone of Pain; only volatile ones hurt, and the more volatile, the more pain. Volatility is a third axis; the zone as drawn is the volatility = 1 plane.
  - **Zone of Uselessness**, around (1, 1): maximally abstract with no dependents. Its contents are detritus, often abstract classes nobody implemented.
- The **Main Sequence** is the line from (1, 0) to (0, 1), the positions farthest from both zones. A component on it is depended on to the extent it is abstract and depends on others to the extent it is concrete. The most volatile components should be kept as far from both zones as possible. The endpoints are best; good architects place most components there. The few components in a large system that are neither fully abstract nor fully stable are best on or near the line.
- **Distance D = |A + I − 1|**, range 0 to 1 (formerly D′). D = 0 is on the Main Sequence; D = 1 is as far as possible. Uses:
  1. Compute D for every component; reexamine and restructure any component whose D is not near 0.
  2. Compute the mean and variance of D across components; a conforming design has both near 0. Use the variance to set control limits (for example, more than one standard deviation from the mean) to flag exceptional components: very abstract with few dependents, or very concrete with many dependents.
  3. Track each component's D over releases against a threshold (for example, 0.1). When it is crossed, find out why strange dependencies crept in.
- These metrics measure conformance to a pattern of dependency and abstraction the author considers good, from experience. A metric is not a god; it measures against an arbitrary standard and is imperfect at best, though hopefully useful.

## 5 Architecture: shape, purpose, and options

### 5.1 The architect

- A software architect is a programmer and stays one. The idea that architects step back from code to focus on higher-level issues is false: architects cannot do the job without experiencing the problems they create for other programmers. They may write less code, but they still take programming tasks. Architects are the best programmers, and they also guide the team toward a design that maximizes productivity.

### 5.2 What architecture is for

- The **architecture** of a system is the shape its builders give it: the division into components, the arrangement of those components, and the ways they communicate. The purpose of the shape is to make the system easy to develop, deploy, operate, and maintain. The strategy is to **leave as many options open as possible, for as long as possible**.
- Architecture has very little to do with whether a system works. Many terribly structured systems work fine; their troubles are in deployment, maintenance, and ongoing development. Architecture's role in correct behavior is critical but passive and cosmetic; it can leave few, if any, behavioral options open. Working correctly must still be one of the highest priorities it supports.
- The primary purpose of architecture is to support the life cycle of the system: make it easy to understand, develop, maintain, and deploy. The ultimate goal is to minimize the lifetime cost of the system and maximize programmer productivity.
- A good architecture supports four things: use cases and operation, maintenance, development, and deployment. It balances them with one component structure that satisfies them all.
  - **Use cases.** Supporting the intent of the system is the architect's first concern and the architecture's first priority. Since architecture has little influence on behavior, the most important thing it can do is expose behavior, making the system's intent visible at the architectural level. A shopping cart application with a good architecture looks like a shopping cart application: its **use cases** are first-class elements (classes, functions, or modules) at the top level, with names that say what they do, so developers need not hunt for behavior.
  - **Operation.** Here architecture plays a bigger role: if the system must handle 100,000 customers per second, or query big data cubes in milliseconds, the structure must support that for each use case that needs it. Needs may call for many small services on many servers, many lightweight threads in one process, a few isolated processes, or one monolithic program. Still, operational problems can usually be solved by adding hardware without drastic architectural change. Hardware is cheap and people are expensive, so an architecture that hinders operation costs less than one that hinders development, deployment, or maintenance. An architecture tuned for operation is still desirable, but the cost balance leans the other way.
  - **Development.** A system hard to develop is unlikely to live long. Team structure matters: a small team of about five can build a monolith with no well-defined components or interfaces and would likely find architectural structure an impediment early on. This is why many systems lack good architecture: they began with none. Several teams (say five teams of seven) cannot progress without well-defined components with reliably stable interfaces. Driven only by schedule, teams drift to one component per team, which is unlikely to be best for deployment, operation, and maintenance. **Conway's law**: any organization that designs a system produces a design whose structure copies the organization's communication structure. A many-team organization needs well-isolated, independently developable components allocated to teams, so teams do not interfere.
  - **Deployment.** The goal is **immediate deployment**: a system deployable in a single action right after build, with no dozens of configuration scripts, property-file tweaks, or hand-made directories. The higher the cost of deployment, the less useful the system. It is achieved by proper partitioning and isolation of components, including master components that start, integrate, and supervise the others. Deployment is seldom considered early, which yields systems easy to develop but hard to deploy. Example: a team picks micro-services early because firm boundaries make development easy, then finds the number of services daunting and their connections and start-up timing a huge source of errors; considering deployment early might have led to fewer services, a hybrid of services and in-process components, and better-managed interconnections.
  - **Maintenance.** Maintenance is the most costly part of any system. Its main costs are **spelunking** (digging through code to find where and how to add a feature or fix a defect) and **risk** (the chance of creating defects while changing things). Separating the system into components isolated by stable interfaces lights the way for new features and greatly reduces the risk of breakage.
- The balance is hard because the use cases, operational limits, team structure, and deployment needs are usually not all known, and they change over the life of the system. Some principles are cheap to apply and help even without a clear picture: partition the system into well-isolated components that leave options open. A good architecture makes the system easy to change, in every way it must change, by leaving options open.

### 5.3 Policy and details

- Structure is the greater of software's two values because it is what makes software soft, and softness depends on the shape of the system, the arrangement of its components, and how they connect. The way to keep software soft is to leave as many options open as possible, for as long as possible. The options to leave open are the details that do not matter.
- Every system splits into two major elements: **policy** and **details**. Policy embodies all the business rules and procedures; it is where the system's true value lives. Details are what let humans, other systems, and programmers communicate with the policy without affecting its behavior at all: IO devices, databases, web systems, servers, frameworks, communication protocols, and so on.
- The architect's goal is to make policy the most essential element and make details irrelevant to it, so decisions about details can be delayed. Decisions that need not be made early, if the policy is kept unaware of them: which database (relational, distributed, hierarchical, flat files); which web server or web technology, or whether to use the web at all; whether to use REST, micro-services, or SOA frameworks; which dependency injection framework.
- The longer you wait to decide a detail, the more information you have to decide it well, provided the policy was built without committing to the detail. Open options also let you run experiments, such as connecting a database-agnostic part of the policy to several databases to compare fit and performance.
- If the company has already committed to a database, web server, or framework, a good architect pretends the decision has not been made and shapes the system so it can still be deferred or changed for as long as possible. **A good architect maximizes the number of decisions not made.**
- Examples:
  - Device independence (see §2.3) was the birth of the OCP. Programs written against the operating system's abstract unit-record functions could have their output redirected from an expensive mainframe's line printer to magnetic tape; the tapes drove offline printers around the clock, while programs could still be tested on the local printer. The policy (formatting name-and-address records) was disconnected from the detail (the device), and the device decision was deferred.
  - An accounting system hard-wired the disk's cylinder/head/sector structure into all its business rules, indices, and linked lists, so a disk upgrade required changes everywhere. The fix was **relative addressing**: treat the disk as a linear array of sectors numbered by integers, with one small routine converting to physical addresses. The policy became agnostic of the disk.
- **Good architects separate details from policy, then decouple the policy from the details so thoroughly that the policy has no knowledge of and no dependence on them, and design the policy so decisions about details can be delayed as long as possible.**

### 5.4 Independence: layers and use cases

- The architect may not know all the use cases but knows the basic intent of the system (shopping cart, bill of materials, order processing). Within that intent, apply SRP and CCP: separate things that change for different reasons, and collect things that change for the same reasons.
- Separate by reason for change:
  - UIs change for reasons unrelated to business rules. Use cases contain both, so separate each use case's UI parts from its business-rule parts, while keeping the use cases visible.
  - **Application-specific business rules** (such as input field validation) are tied to the application. **Application-independent business rules** (such as interest calculation or inventory counting) belong to the domain. They change at different rates for different reasons, so separate them.
  - The database, query language, and schema are technical details unrelated to business rules or UI; they change for their own reasons, so separate them.
- The result is **decoupled horizontal layers**, for example: UI, application-specific business rules, application-independent business rules, database. (These four are examples, not a complete list.)
- Use cases themselves change for different reasons and at different rates (add-order versus delete-order), so they are a natural way to divide the system. Each use case is a thin **vertical slice** that cuts through the layers, using some UI, some application-specific rules, some application-independent rules, and some database. So the system is divided both into horizontal layers and into vertical use cases. To decouple use cases, separate add-order's UI from delete-order's UI, and likewise their business rules and database parts, down the full height of the system.
- Benefits of this decoupling:
  - New use cases can be added without disturbing old ones, especially if UI and database are grouped to support each use case separately.
  - Operation: high-throughput parts are likely already separated from low-throughput ones, and if UI and database are separate from business rules they can run on different servers, with high-bandwidth parts replicated.
  - Development: if business rules do not know about the UI, the UI team cannot much affect the business-rules team; decoupled use cases keep an addOrder team from interfering with a deleteOrder team. This works for any team organization: feature teams, component teams, layer teams, or others.
  - Deployment: if decoupling is done well, layers and use cases could be hot-swapped in a running system, and adding a use case could be as simple as adding a few jar files or services.

### 5.5 True and accidental duplication

- Architects often fall into a trap driven by fear of duplication.
- **True duplication**: every change to one copy requires the same change to every copy. Professionals are honor-bound to eliminate true duplication; it is generally bad. **Accidental duplication** (false duplication): code that looks the same but evolves along different paths, changing at different rates for different reasons; after a few years the copies are very different.
- Two use cases with very similar screens are most likely accidental duplicates. Do not unify them, or separating them later will be hard. When separating use cases vertically, resist the knee-jerk removal of duplication in similar screens, algorithms, queries, or schemas; make sure the duplication is real before coupling.
- When separating layers horizontally, do not pass a database record up to the UI because it resembles the screen's structure. Create a separate **view model** and copy the elements across. The similarity is almost certainly accidental, and a view model costs little and keeps the layers decoupled.

### 5.6 Decoupling modes

- For the operational benefit, decoupling must have the right **decoupling mode**. Components on separate servers cannot share an address space; they must be independent services talking over a network.
- The three modes:

  | Mode | What is controlled | How components communicate |
  |---|---|---|
  | **Source-level** | Dependencies between source modules, so a change to one does not force changes or recompiles of others (for example, Ruby Gems) | Function calls in one address space, one executable (a **monolith**) |
  | **Deployment-level** | Dependencies between deployable units (jar files, DLLs, shared libraries, Gems), so a source change in one does not force others to be rebuilt and redeployed | Function calls in one address space, or IPC, sockets, or shared memory between processes on one processor |
  | **Service-level** | Dependencies reduced to data structures only | Network packets only; each execution unit is independent of source and binary changes in the others |

- A **service** (or micro-service, by some vague notion of line count) is a component separated to the level of an independent execution unit on the network. An architecture based on services is a service-oriented architecture (SOA). SOA is not claimed to be the best architecture, nor micro-services the future; sometimes components must be separated all the way to services.
- **The decoupling mode is one of the options a good architecture leaves open.** The same holds for the choice among threads, processes, services, and monolith: a monolith that depends on being a monolith cannot easily become multiple processes, threads, or micro-services, while an architecture that isolates its components and does not assume how they communicate can transition as operational needs change.
- The best mode is hard to know early, and it may change as the project matures. Decoupling at the service level by default (popular at the time of writing) is expensive and encourages coarse-grained decoupling; however "micro" the services, the decoupling is unlikely to be fine enough. Service boundaries cost development time and system resources; where none are needed they waste effort, memory, and cycles. Memory and cycles are cheap; effort is not.
- Preferred approach:
  1. Push decoupling to the point where a service could be formed if necessary, but keep components in the same address space as long as possible.
  2. Start with source-level separation. It may be enough for the life of the project.
  3. If deployment or development problems arise, move some decoupling to the deployment level.
  4. As development, deployment, and operational problems grow, carefully choose which deployable units to turn into services, and shift gradually.
  5. If operational needs decline, slide back to deployment-level or source-level decoupling.
- A good architecture lets a system be born as a monolith in a single file, grow into independently deployable units, then into services, and later reverse back to a monolith. It protects most of the source code from changes in decoupling mode, so large deployments can use one mode and small ones another. Changing modes need not be a trivial configuration option (though sometimes that fits); the point is that the mode will likely change, and a good architect foresees and facilitates the change.

## 6 Boundaries

### 6.1 Drawing lines

- Software architecture is the art of drawing lines called **boundaries**. A boundary separates software elements and keeps those on one side from knowing about those on the other.
- Some boundaries are drawn very early, even before code; others much later. Early ones exist to defer decisions and keep them from polluting the core business logic.
- What saps the people-power the architect must conserve is coupling, especially coupling to **premature decisions**: decisions that have nothing to do with the business requirements (the use cases), such as frameworks, databases, web servers, utility libraries, and dependency injection. A good architecture makes these decisions ancillary and deferrable, does not depend on them, and lets them be made at the latest possible moment without significant impact.
- Examples of premature decisions (the author has seen this many times):
  - Company P moved a desktop app to the web with a three-tier distributed design: every domain object existed in GUI, middleware, and database tiers with marshaled messages between them. Adding one field meant changing three tiers, four message protocols, eight protocol handlers, and three executables. They never sold a system that needed a server farm; every deployment was one server, still doing all the marshaling. Three-tier is not an architecture; it is a **topology**, exactly the kind of decision a good architecture defers.
  - Company W's architect imposed full enterprise SOA with a huge domain model and a suite of domain-object services. Adding a contact to a sales record needed a service registry lookup and messages with dozens of fields the programmer had to fake; testing needed all services, a message bus, and a BPEL server running. Nothing is wrong with a system built around services; the error was the premature adoption and enforcement of a tool suite promising SOA.
- Example of good deferral (FitNesse):
  - The "Download and Go" rule (users download no more than one jar file) drove decisions. A bare-bones home-written web server postponed any web framework decision; one was slipped in years later.
  - An interface (WikiPage) stood between all data access and the repository. Stubs were used for three months, an in-memory hash table for a full year (the whole first version worked without saving), then flat files. The planned MySQL was dropped entirely: the decision was deferred into nonexistence. A customer who wanted MySQL wrote a MySQL implementation of the interface and had it working in a day; the boundary did not block the original direction.
  - With no database for 18 months, there were no schema, query, server, password, or connection problems, and all tests ran fast.
- **Drawing boundaries delays and defers decisions and saves enormous time and headaches.**

### 6.2 Which lines to draw

- Draw lines between things that matter and things that do not: between the GUI and the business rules, between the database and the GUI, and between the database and the business rules. Each does not matter to the other.
- The belief that the database is inseparable from the business rules, or even embodies them, is wrong. The database is a tool the business rules use indirectly. They need not know the schema, query language, or other details, only that some functions fetch and save data.
- Method: BusinessRules use a DatabaseInterface to load and save data; DatabaseAccess implements it and directs the actual Database. The boundary runs across the inheritance relationship, just below DatabaseInterface. Arrows leave DatabaseAccess, so no other class knows it exists. At the component level, DatabaseInterface lives in the BusinessRules component and DatabaseAccess in the Database component: the Database knows the BusinessRules, not the reverse. (The classes are symbolic; a real system has many, following the same pattern.)
- The arrow's direction means the Database does not matter to the BusinessRules, but the Database cannot exist without them, because it holds the code that translates business-rule calls into the query language. So the Database can be replaced by any implementation (Oracle, MySQL, Couch, Datomic, flat files), and the database decision can be deferred while business rules are written and tested first.
- **The IO is irrelevant.** Developers and customers often mistake the GUI for the system and expect to see it working at once; it is not the system. Example: a video game feels like its interface, but behind it a model of data and functions would run and model every event without ever being displayed.
- Across a boundary, the less relevant component depends on the more relevant one. The arrows show who knows about, and so cares about, whom. The GUI cares about the business rules, so any other interface could replace it without the business rules caring.

### 6.3 Plugin architecture

- **Plugin architecture**: the core business rules are kept separate from and independent of the components that are optional or can take many forms (such as UI and database); those components plug in to the business rules. The history of software technology is the story of how to make plugins conveniently, to get a scalable and maintainable architecture.
- With the UI as a plugin, any UI can be used: web, client/server, SOA, console. With the database as a plugin, any SQL, NoSQL, file-system, or future database can be used. Replacement may not be trivial (a web-first system may need some UI/business-rule communication reworked to get a client-server UI), but the plugin architecture at least makes the change practical.
- Example: ReSharper depends on Visual Studio. The ReSharper team can do nothing to disturb the Visual Studio team, but Visual Studio could disable ReSharper completely. The dependency structure decides which side is immune.
- Systems should have this asymmetry: some modules immune to others, so business rules do not break when a page format or schema changes. A plugin architecture creates **firewalls** across which changes cannot propagate.
- **Boundaries are drawn where there is an axis of change**: the components on one side change at different rates and for different reasons than those on the other (GUI versus business rules; business rules versus dependency injection frameworks). This is the SRP again; the SRP tells you where to draw boundaries.
- Procedure:
  1. Partition the system into components. Some are core business rules; others are plugins holding necessary functions not directly related to the core business.
  2. Arrange the code so the arrows between components point one way: toward the core business.
  This is the DIP and the SAP applied: dependency arrows point from lower-level details to higher-level abstractions.

### 6.4 Boundary anatomy: the kinds of boundaries

- A system's architecture is a set of components and the boundaries that separate them. Boundaries come in many forms.
- At runtime a **boundary crossing** is just a function on one side calling a function on the other side and passing data. The trick to a good crossing is managing source code dependencies, because a change to one source module may force other modules to change or be recompiled and redeployed; building firewalls against that is what boundaries are for.
- The two crossing directions:
  - A low-level client calls a higher-level service: runtime and source code dependencies both point toward the higher-level side, and the passed data structure is defined on the called (higher-level) side.
  - A high-level client must call a lower-level service: use dynamic polymorphism to invert the dependency. The client calls ServiceImpl through a Service interface; all dependencies cross toward the higher-level side, and the data structure is defined on the calling (higher-level) side.
- The four kinds, weakest to strongest:

  | Kind | Physical form | Communication cost |
  |---|---|---|
  | Monolith (source-level) | none; one executable | function calls; cheap, can be chatty |
  | Deployment components | dynamically linked libraries | function calls (plus a one-time linking/loading hit); can be chatty |
  | Local processes | separate address spaces on the same processor(s) | OS calls, marshaling, context switches; moderately expensive, limit chattiness |
  | Services | location-independent processes; all communication over the network | tens of milliseconds to seconds; avoid chattiness, handle latency |

- **Monolith.** The simplest and most common boundary has no physical form: a disciplined separation of functions and data in one processor and address space (source-level decoupling), deployed as one executable (a statically linked C/C++ program, an executable jar, a single .NET EXE). Invisible boundaries are not absent or meaningless: even statically linked, the ability to develop components independently and assemble them at the end is immensely valuable; teams work independently, and high-level components stay independent of details. Monolith components are usually delivered as source code, because deployment requires compiling and linking.
  - Monoliths almost always manage internal dependencies with dynamic polymorphism; this is one reason OO became so important. Without OO or equivalent polymorphism, architects must use dangerous function pointers, and most find that too risky and give up on partitioning altogether.
  - Static polymorphism (generics, templates) can sometimes manage dependencies in a monolith, especially in C++, but it cannot spare recompilation and redeployment the way dynamic polymorphism does. It is not an option for deployment components.
- **Deployment components.** The simplest physical boundary is a dynamically linked library (.NET DLL, Java jar, Ruby Gem, UNIX shared library), delivered in binary form without compiling; deployment means gathering the units (a WAR file, a directory). Apart from binary delivery they behave like a monolith: same address space, same segregation and dependency strategies.
- **Threads** are not boundaries or deployment units. They organize the schedule and order of execution and may sit inside one component or span many.
- **Local processes.** A much stronger boundary: a process started from the command line (or an equivalent system call) running on the same processor(s) in a separate address space, with memory protection usually preventing sharing (though shared memory partitions are common). They talk through sockets or OS facilities such as mailboxes and message queues. A local process may be a statically linked monolith or built from dynamically linked components; think of it as an uber-component. Source code dependencies across the boundary point the same way as before, toward the higher-level side. The higher-level process's source must not contain the names, physical addresses, or registry lookup keys of lower-level processes, because the goal is for lower-level processes to be plugins to higher-level ones.
- **Services.** The strongest boundary: a process that does not depend on its physical location and assumes all communication is over the network. Lower-level services plug in to higher-level services, and higher-level service source code must contain no physical knowledge (such as a URI) of any lower-level service.
- Most systems other than monoliths use more than one kind. A service is often just a facade for several local processes, and a service or local process is almost certainly either a monolith of source components or a set of dynamically linked components. Boundaries are often a mix of local chatty ones and ones more concerned with latency.

## 7 Policy, level, and business rules

### 7.1 Policy and level

- A software system is a statement of **policy**: at its core, a program is a detailed description of the policy by which inputs are transformed into outputs. In nontrivial systems the policy breaks into many smaller policies: how business rules are calculated, how reports are formatted, how input is validated.
- Part of the art of architecture is separating policies and regrouping them by how they change. Policies that change for the same reasons at the same times are at the same level and belong in the same component. Policies that change for different reasons or at different times are at different levels and belong in different components. The regrouped components often form a DAG: nodes are components of same-level policies, edges are dependencies between levels. These are source code (compile-time) dependencies: import in Java, using in C#, require in Ruby.
- In a good architecture, dependency direction is set by level: **low-level components always depend on high-level components.**
- **Level** (strict definition): distance from the inputs and outputs. The farther a policy is from both, the higher its level. Policies that manage input and output are the lowest level.
- Data flow and source code dependencies do not always point the same way. Source code dependencies should be decoupled from data flow and coupled to level.
- Example: an encryption program reads characters, translates them through a table, and writes them. Translate is the highest-level component, farthest from IO; such a top component is called the **Central Transform**. Writing encrypt() as a loop calling writeChar(translate(readChar())) is wrong, because high-level encrypt then depends on low-level readChar and writeChar. Better: an Encrypt class plus CharReader and CharWriter interfaces form the high-level unit, with all dependencies crossing its border pointing inward; ConsoleReader and ConsoleWriter implement the interfaces. The encryption policy then works in many contexts, and IO changes are unlikely to affect it. The Encryption component knows nothing of the IODevices component; IODevices depends on Encryption.
- Higher-level policies (far from IO) tend to change less often and for more important reasons. Lower-level policies (near IO) tend to change more often and more urgently, for less important reasons. Even in the encryption program, the IO devices are far more likely to change than the algorithm. So keeping levels separate, with all source code dependencies pointing toward higher levels, means trivial but urgent low-level changes have little or no effect on the important higher levels. **Lower-level components should be plugins to higher-level components.**
- This combines SRP, OCP, CCP, DIP, SDP, and SAP; grouping policies by how they change is the SRP and CCP.

### 7.2 Business rules

- **Business rules**, strictly, are rules or procedures that make or save the business money. Very strictly, they would make or save money even if done by hand. Example: a bank charging N% interest on a loan makes money whether a program or a clerk with an abacus computes it.
- **Critical Business Rules** are rules critical to the business itself that would exist even with no system to automate them. **Critical Business Data** is the data those rules need that would exist even without automation (for a loan: balance, interest rate, payment schedule). The two are inseparably bound, so they are good candidates to combine into one object.
- An **Entity** is an object in the system that embodies a small set of Critical Business Rules operating on Critical Business Data. It contains the data or has very easy access to it, and its interface is the functions implementing those rules. Example: a Loan Entity holds principle, rate, and period and offers makePayment, applyInterest, and chargeLateFee.
- An Entity gathers the software for one business-critical concept and separates it from every other concern. It must be free of concerns about databases, user interfaces, and third-party frameworks, so it can stand alone as a representative of the business and serve any system, regardless of presentation, storage, or how computers are arranged. It is pure business. No OO language is required: an Entity is just Critical Business Data and Critical Business Rules bound in one separate module.
- **Application-specific business rules** make or save money by defining and constraining how an automated system works. They would not exist in a manual environment. Example: loan officers may not see the payment estimate screen until contact information is gathered and validated and the credit score is confirmed at 500 or higher.
- A **use case** describes how an automated system is used: the user's input, the output returned, and the processing steps that produce it. Use cases hold application-specific business rules; Entities hold Critical Business Rules. Use cases specify how and when the Entities' rules are invoked: they control the dance of the Entities.
- Example use case, "Gather Contact Info for New Loan": input name, address, birthdate, driver's license number, SSN; output the same for readback plus credit score. Steps: (1) accept and validate name; (2) validate address, birthdate, license, SSN; (3) get credit score; (4) if score < 500, activate Denial; (5) else create Customer (the Customer Entity) and activate Loan Estimation.
- A use case does not describe the user interface, except informally naming the data in and out. From a use case you cannot tell whether the system is delivered on the web, a thick client, a console, or as a pure service. This matters because how data gets in and out is irrelevant to the rules governing users and Entities.
- A use case is an object: one or more functions implementing application-specific rules, plus data (input, output, and references to the Entities it uses).
- Entities know nothing of the use cases that control them; use cases depend on Entities. This is the DIP: Entities are higher level because they are generalizations usable in many applications, so they are farther from inputs and outputs; use cases are specific to one application, so they are closer.
- A use case must have no inkling of how data reaches the user or any other component. Use case code must not know about HTML or SQL.
- **Request and response models** are the simple input and output data structures a use case accepts and returns. They depend on nothing: they do not derive from framework types such as HttpRequest or HttpResponse and know nothing of the web or any UI. Their independence is critical, because dependencies are transitive: if the models carry dependencies, every use case using them is bound to those dependencies.
- **Do not let request or response models contain references to Entities**, even though they share much data; avoid the temptation. Their purposes differ and they will change for different reasons; tying them together violates CCP and SRP and produces lots of **tramp data** and conditionals.
- Business rules are the reason the system exists; they are the core functionality, the code that makes or saves money. Ideally they are the heart of the system, pristine, free of UI and database concerns, with lesser concerns plugged into them, and they are the most independent and reusable code in the system.

### 7.3 Screaming architecture

- A building's plans reveal its purpose: a house's plans scream "home," a library's plans scream "library." Likewise, an application's top-level directory structure and highest-level packages should scream its domain ("Health Care System," "Accounting System," "Inventory Management System"), not its framework ("Rails," "Spring/Hibernate," "ASP"). This is **screaming architecture**.
- Architecture is the structure that supports the use cases, so it should scream the use cases. Architectures are not about frameworks and should not be supplied by them. Frameworks are tools to use, not architectures to conform to: if the architecture is based on a framework, it cannot be based on the use cases. Good architectures center on use cases so the structure can be described without committing to frameworks, tools, and environments.
- A house architect makes sure the house is usable before choosing brick, stone, or cedar; the owner decides those later. A good software architecture likewise lets decisions about frameworks, databases, web servers, and other tools be deferred, makes it unnecessary to choose Rails, Spring, Hibernate, Tomcat, or MySQL until much later, and makes it easy to change those choices. Frameworks are options to be left open.
- The web is not an architecture. It is a **delivery mechanism** (an IO device), a detail that must not dominate the structure, and the decision to deliver over the web should be deferred. The architecture should be as ignorant as possible of how it is delivered: it should be deliverable as a console app, web app, thick client, or web service without undue change to its fundamentals.
- Framework authors and followers tend to present frameworks as true believers, assuming the framework does everything. Do not take that position. Look at each framework with a jaded, skeptical eye: what does it cost, how should you use it, how do you protect yourself from it, and how do you keep it from taking over the architecture while preserving the emphasis on use cases.
- **Testable architecture**: if the architecture is about use cases and frameworks are kept at arm's length, all use cases can be unit-tested with no framework in place: no running web server, no connected database. Entities are plain old objects with no dependencies on frameworks or databases; use case objects coordinate them; all can be tested in place.
- Test of a screaming architecture: new programmers looking at the repository should immediately think "this is a health care system," be able to learn all the use cases, and still not know how it is delivered. Views and controllers are details decided later.

## 8 The Clean Architecture

### 8.1 Goals

- Several earlier architectures — **Hexagonal Architecture** (also called Ports and Adapters; Cockburn), DCI (Coplien and Reenskaug), and BCE (Jacobson) — differ in detail but share one aim: separation of concerns, achieved by dividing software into layers, with at least one layer for business rules and another for user and system interfaces. The **Clean Architecture** integrates them into one actionable idea.
- Such architectures produce systems that are:
  - **Independent of frameworks**: frameworks are tools, and the system is not crammed into their constraints.
  - **Testable**: business rules can be tested without the UI, database, web server, or any other external element.
  - **Independent of the UI**: a web UI can be replaced by a console UI without changing the business rules.
  - **Independent of the database**: Oracle or SQL Server can be swapped for Mongo, BigTable, CouchDB, or something else.
  - **Independent of any external agency**: the business rules know nothing at all about the interfaces to the outside world.

### 8.2 The circles and the Dependency Rule

- Picture concentric circles, from inside out:
  1. **Entities** (enterprise business rules)
  2. **Use cases** (application business rules)
  3. **Interface adapters** (controllers, gateways, presenters)
  4. **Frameworks and drivers** (devices, web, UI, database, external interfaces)
  The farther in, the higher the level. Outer circles are mechanisms; inner circles are policies. The outermost circle holds low-level concrete details; the innermost is the most general and highest level.
- **The Dependency Rule: source code dependencies must point only inward, toward higher-level policies.** It is the overriding rule that makes the architecture work.
  - Nothing in an inner circle can know anything at all about something in an outer circle. Code in an inner circle must never mention the name of anything declared in an outer circle: no function, class, variable, or any other named entity.
  - Data formats declared in an outer circle must not be used by an inner circle, especially formats generated by a framework, because nothing in an outer circle should affect the inner circles.
- **Entities** encapsulate enterprise-wide Critical Business Rules. An Entity can be an object with methods or a set of data structures and functions, as long as many applications in the enterprise can use it. With no enterprise, only one application, the Entities are that application's business objects. They hold the most general, highest-level rules and are the least likely to change when something external changes: a change to page navigation or security must not affect them, nor any operational change to any one application.
- The **use cases** layer holds application-specific business rules. It implements all the use cases, which orchestrate data to and from the Entities and direct them to apply their Critical Business Rules. Changes here must not affect the Entities, and this layer must not be affected by changes to the database, UI, or common frameworks. Changes to how the application operates, and to a use case's details, will affect this layer.
- The **interface adapters** layer converts data between the form most convenient for the use cases and Entities and the form most convenient for an external agency such as the database or the web. It wholly contains the MVC of a GUI: presenters, views, and controllers; the models are probably just data structures passed between controllers, use cases, and presenters. No code inward of this circle may know anything about the database; if it is SQL, all SQL stays in this layer, in the parts that deal with the database. It also holds any adapter that converts data from an external form (such as an external service) to the internal form.
- The **frameworks and drivers** layer is the outermost: frameworks and tools such as the database and the web framework. You generally write little code there beyond glue that talks to the next circle in. All the details go there, so they can do little harm.
- Four circles is a schematic. You may need more; there is no rule that there must be exactly four. The Dependency Rule always applies.

### 8.3 Crossing the circles

- Flow of control may start in the controller, pass through the use case, and end in the presenter, while all source code dependencies point inward. A direct call from use case to presenter would violate the Dependency Rule, so the use case calls an interface in the inner circle (the **output port**) and the presenter, in the outer circle, implements it. This is the DIP. The same technique crosses every boundary: dynamic polymorphism makes source code dependencies oppose the flow of control, so the Dependency Rule holds whichever way control flows.
- Data crossing boundaries is simple, isolated data structures: basic structs, simple data transfer objects, function arguments, a hashmap, or a constructed object.
- **Do not cheat by passing Entity objects or database rows across boundaries.** The data structures must have no dependency that violates the Dependency Rule. Example: database frameworks often return a convenient row structure; passing it inward forces the inner circle to know about an outer circle.
- Data crossing a boundary is always in the form most convenient for the inner circle.
- Typical scenario (web system in Java with a database):
  1. The web server gathers user input and hands it to the Controller.
  2. The Controller packs it into a plain object (Input Data) and passes it through the InputBoundary interface (the **input port**) to the UseCaseInteractor.
  3. The **interactor** (the object that implements a use case) interprets it and controls the dance of the Entities, using a DataAccessInterface to bring Entity data from the Database into memory.
  4. When done, it gathers data from the Entities into Output Data (another plain object).
  5. The Output Data passes through the OutputBoundary interface to the Presenter.
  6. The Presenter repackages it into a ViewModel (another plain object), mostly Strings and flags: Dates and Currency become formatted Strings; button and menu names, and flags saying which are grayed out, go there too.
  7. The View moves the ViewModel data into the HTML page, with almost nothing else to do.
  InputBoundary, OutputBoundary, Input Data, and Output Data belong to the interactor's side. The Controller uses InputBoundary (implemented by the interactor); the Presenter implements OutputBoundary (used by the interactor); the DataAccess class implements DataAccessInterface, owned by the inner side. Every dependency crosses the boundary lines pointing inward.
- Layering plus the Dependency Rule gives a system that is intrinsically testable, and when an external part (database, web framework) becomes obsolete it can be replaced with minimal fuss. The rules are not hard to follow and save many headaches.

## 9 Boundary techniques

### 9.1 Humble objects

- The **Humble Object pattern** splits behavior into two modules: a humble one holding all the hard-to-test behavior stripped to its barest essence, and another holding all the testable behavior stripped out of the humble one. It was first found as a unit-testing aid.
- GUIs are hard to unit test because tests cannot easily see the screen, but most GUI behavior is easy to test. So split it:
  - The **view** is the humble, hard-to-test part. Its code is as simple as possible; it moves data into the GUI without processing it.
  - The **presenter** is the testable part. It accepts data from the application and formats it for display into a simple data structure, the **view model**, which the view just moves to the screen. Examples: a Date becomes a formatted string; Currency becomes a string with proper decimals and markers; a flag says whether a negative number shows red; button and menu names become strings; graying-out becomes booleans; tables of numbers become tables of formatted strings.
  - Everything on the screen that the application controls should appear in the view model as a string, boolean, or enum, leaving the view nothing to do but load it. That is what makes the view humble.
- Testability has long been known as an attribute of good architecture. The split into testable and non-testable parts often defines an architectural boundary; presenter/view is one of many.
- **Database gateways** sit between interactors and the database. They are polymorphic interfaces with one method for each create, read, update, or delete the application performs, named for application needs. Example: to get the last names of users who logged in yesterday, a UserGateway has getLastNamesOfUsersWhoLoggedInAfter(Date) returning a list of names.
  - **SQL is not allowed in the use cases layer.** Use cases call gateway interfaces; classes in the database layer implement them. The implementation is the humble object: it just uses SQL (or whatever the database interface is) to get the data each method needs.
  - Interactors are not humble, since they hold application-specific business rules, but they are testable because gateways can be replaced with stubs and test doubles.
- There is no such thing as an object relational mapper (ORM), because objects are not data structures, at least from their users' view. To its users an **object** is a set of operations; its data is private. A **data structure** is a set of public data with no implied behavior. ORMs would better be called **data mappers**: they load data from relational tables into data structures. They belong in the database layer, forming another humble object boundary between the gateway interfaces and the database.
- Service communication is another humble object boundary. Output: the application loads data into simple data structures, which pass to modules that format and send them to external services. Input: **service listeners** receive data from the service interface, format it into a simple data structure the application can use, and pass it across the boundary.
- At each architectural boundary a humble object is likely nearby. Communication across the boundary almost always uses a simple data structure, and the boundary often divides something hard to test from something easy to test. Using humble objects at boundaries vastly increases the testability of the whole system.

### 9.2 Partial boundaries

- A **full boundary** is expensive. It needs reciprocal polymorphic boundary interfaces (isolating both directions), input and output data structures, and all the dependency management needed to isolate the two sides into independently compilable and deployable components. That is a lot of work to build and to maintain.
- A **partial boundary** is a placeholder for a boundary, used when a full one is judged too expensive but you want to hold a place for it. The Agile community often frowns on such anticipatory design as violating **YAGNI** ("You Aren't Going to Need It"); an architect may answer "Yeah, but I might" and build a partial boundary.
- Three kinds (there are many others):
  1. **Skip the last step.** Do all the work to make independently compilable and deployable components, then compile and deploy them as one component. It costs the same code and design work as a full boundary but avoids administering several components: no version tracking or release management, a difference not to be taken lightly. Example: FitNesse's web server was designed to be separable from the wiki so it could be reused, but shipped in one jar to keep "download and go." Danger: once it is clear the separate component will never be needed, the separation weakens and dependencies start crossing in the wrong direction; re-separating FitNesse's web and wiki parts would now be a chore.
  2. **One-dimensional boundary** (the Strategy pattern). Clients use a ServiceBoundary interface that ServiceImpl classes implement. The dependency inversion is in place, isolating the client from the implementation. Without reciprocal interfaces, nothing but developer discipline prevents a **backchannel** (such as ServiceImpl depending directly on the Client), so it can degrade quickly.
  3. **Facade.** A Facade class lists all services as methods and forwards calls to service classes the client should not touch. It gives up even dependency inversion. The client has a transitive dependency on every service class: in static languages any change to a service class forces the client to recompile, and backchannels are very easy to create.
- Each has its own costs and benefits, each fits some contexts as a placeholder for an eventual full boundary, and each can degrade if the full boundary never comes. Deciding where a boundary might one day exist, and whether to implement it fully or partially, is one of the architect's functions.

### 9.3 Finding boundaries: layers and streams

- It is easy to think of a system as three components: UI, business rules, database. That is enough for some simple systems; most have more.
- Example: a text adventure game ("Hunt the Wumpus"; commands like GO EAST; about 200 lines, so clean architecture would not really be applied to it; it stands in for a much larger system).
  - To support several human languages, the game rules talk to the UI through a language-independent API, and each UI translates it. Any number of UIs can reuse the same rules, which do not know which language is used.
  - Game state may live in flash, the cloud, or RAM; the rules use an API to talk to storage, and the storage implementations depend on the rules.
  - Language is not the only axis of change for the UI; the communication mechanism (shell window, text messages, chat app) is another. **Each axis of change defines a potential architectural boundary.** So an API also isolates language from delivery. Result: SMS and Console implement an abstract Text Delivery API; English and Spanish implement a Language API; Cloud Data and Flash Data implement a Data Storage API; Game Rules is at the top.
- **An API across a boundary is defined and owned by its user (the higher-level side), not by its implementer.** GameRules defines the API that Language implements; Language defines the API that TextDelivery implements. Inside each component of a full boundary are reciprocal polymorphic interfaces: some it uses that the other side implements, and some it implements that the other side uses. Variations (English, SMS, CloudData) are polymorphic interfaces defined in the abstract API component and implemented by the concrete components.
- Arrows in component diagrams show source code dependencies, not data flow. In the game, input rises from TextDelivery through Language (translated into commands) to GameRules, which sends data down to DataStorage; output goes back down through Language to TextDelivery. Drawn with all arrows up, GameRules is at the top because it holds the highest-level policies.
- The data flow splits into **streams**: user communication on one side and persistence on the other, meeting at the top in GameRules, the processor of both (the Central Transform). There are not always two: adding multiplayer networking makes three, and complex systems may have many.
- Streams do not simply meet at one top component; higher-level policies can hide inside what looked like the top. Example: GameRules splits into MoveManagement (lower-level mechanics: cavern connections, object locations, moving the player, detecting events) and PlayerManagement (higher-level: player health, the cost or benefit of events, win or lose). MoveManagement reports events like FoundFood or FellInPit to PlayerManagement. In a massively multiplayer version, MoveManagement runs on the player's computer and PlayerManagement on a server offering a micro-service API, with a full architectural boundary between them (a proxy and an implementation of PlayerManagement, connected over the network).
- **Architectural boundaries exist everywhere**, and architects must recognize when they are needed. Full boundaries are expensive, but boundaries that were ignored are very expensive to add later, even with comprehensive tests and refactoring discipline.
- YAGNI has wisdom, because over-engineering is often much worse than under-engineering. But when you find you truly need a boundary where none exists, adding it can be costly and risky. Resolution: guess intelligently about the future, weighing costs to decide which boundaries to implement fully, partially, or not at all, and keep reevaluating.
- Procedure (ongoing, not one-time):
  1. Watch the system as it evolves.
  2. Note where boundaries may be required.
  3. Watch carefully for the first inkling of friction caused by their absence.
  4. Then weigh the cost of implementing them against the cost of ignoring them.
  5. Review the decision frequently.
  The goal is to implement a boundary at the inflection point where the cost of implementing it becomes less than the cost of ignoring it.

## 10 Special components

### 10.1 Main

- **Main** is the component, present at least once in every system, that creates, coordinates, and oversees the other components. It is the ultimate detail: the lowest-level policy and the system's entry point. Nothing but the operating system depends on it. It is the dirtiest of all dirty components, a low-level module in the outermost circle.
- Main's job:
  1. Create all the factories, strategies, and other global facilities.
  2. Gather outside resources and set up initial conditions and configuration.
  3. Hand control to the high-level abstract parts of the system.
- Dependency injection by a framework should happen in Main. Once dependencies are injected into Main, Main should distribute them normally, without the framework, so knowledge of the framework stays in the dirtiest component.
- Example: in the game, Main holds all the strings (environments, shapes, cavern types) the rest of the code should not know, creates the input stream, runs the loop that interprets text commands, builds the map, and defers all real processing to higher-level components. It creates the game through a factory given only the class name as a string, because that class is even dirtier than Main; naming it by string avoids a source code dependency, so changes there do not force Main to recompile or redeploy.
- Think of Main as a plugin to the application: it sets up conditions and configuration, gathers outside resources, and hands control to the high-level policy. Because it is a plugin, there can be many Mains, one per configuration: Dev, Test, Production, or one per country, jurisdiction, or customer. Putting Main behind an architectural boundary makes configuration much easier.

### 10.2 Services

- Service-oriented and micro-service "architectures" are popular because services seem strongly decoupled and seem to allow independent development and deployment. Both beliefs are only partly true.
- **Services are not, by their nature, an architecture.** Architecture is defined by boundaries that separate high-level policy from low-level detail and follow the Dependency Rule. A service is just a function call across a process or platform boundary. As with functions in a monolith, some service calls cross architectural boundaries and some merely separate behaviors; the latter are little more than expensive function calls. Services that separate functionality across processes and platforms often have real benefits whether or not they obey the Dependency Rule; they just do not define the architecture.
- **The decoupling fallacy**: the belief that services are strongly decoupled because each runs in its own process, cannot touch the others' variables, and has a well-defined interface. Services are decoupled at the level of variables, but they can be coupled through shared resources on a processor or network, and they are strongly coupled by the data they share: if a field is added to a record passed between services, every service using the field must change, and all must agree on its meaning. Service interfaces are no more formal or well-defined than function interfaces.
- **The fallacy of independent development and deployment**: the belief that services, each owned by a dedicated dev-ops team, make development and operation scalably partitionable across many services and teams. Large enterprise systems have been built from monoliths and component systems too, so services are not the only way to scale. To the extent services are coupled by data or behavior, their development, deployment, and operation must be coordinated. Organizing many small teams each owning a few micro-services tends to make the number of micro-services about equal to the number of programmers.
- Example (the kitty problem): a taxi aggregator is built as micro-services (TaxiUI; TaxiFinder, which checks supplier inventories and stores candidates; TaxiSelector, which applies the user's criteria; TaxiDispatcher, which orders the taxi). Marketing adds kitten delivery: only some suppliers take part, drivers allergic to cats must never be chosen, and vehicles that carried kittens in the last 3 days must not be chosen for customers who declare allergies. Every service must change, and development and deployment must be coordinated: the services were all coupled.
- **Cross-cutting concerns** affect every system, service-based or not. Functional decompositions (like a pipeline of services by function) are very vulnerable to new features that cut across all the functions.
- Fix with SOLID: make classes polymorphically extendable. Keep generic logic in abstract base classes in the original components; move ride-specific logic to a Rides component; put the new feature in a Kittens component; have these override the abstract bases (Template Method or Strategy); keep dependencies following the Dependency Rule; have the UI create the feature classes through factories. Then the kitty feature changes only TaxiUI; everything else is a new jar, Gem, or DLL loaded at runtime, so the feature is developed and deployed independently.
- Services need not be little monoliths. Design them with SOLID and an internal component structure so new components can be added without changing existing ones. Think of a Java service as a set of abstract classes in jar files, and each new feature as another jar of classes extending them; deploying a feature means adding jars to load paths, not redeploying services. Adding features then follows the OCP.
- **Architectural boundaries do not fall between services. They run through services, dividing them into components.** To handle cross-cutting concerns, services need internal component architectures that follow the Dependency Rule; those components, not the services, define the system's architectural boundaries.
- Services are useful for scalability and developability but are not in themselves architecturally significant. Architecture is the boundaries drawn in a system and the dependencies that cross them, not the physical mechanisms by which elements communicate and execute. A service may be a single component wholly inside a boundary, several components separated by boundaries, or (rarely, though less rarely than one would hope) so coupled to its clients that it has no architectural significance.

### 10.3 Tests

- Tests are part of the system and participate in the architecture like every other part. Architecturally, all tests are the same: tiny TDD tests and large FitNesse, Cucumber, SpecFlow, or JBehave tests (unit, integration, acceptance, functional, BDD, component) are equivalent.
- Tests follow the Dependency Rule by nature. They are detailed and concrete and always depend inward on the code under test. They are the outermost circle; nothing in the system depends on them. They are independently deployable (usually to test systems, not production), even in systems that otherwise need no independent deployment. They are the most isolated component: no user depends on them and they support development, not operation. Yet they are a full system component and in many ways the model every other component should follow.
- Treating tests as outside the system's design is catastrophic. Tests not integrated into the design tend to be fragile and make the system rigid. The issue is coupling: tests strongly coupled to the system must change with it.
- **The Fragile Tests Problem**: changes to common components break hundreds or thousands of tests. Example: tests that verify business rules through the GUI, starting at the login page and navigating, all break when the login page or navigation changes. Fragile tests make the system rigid: developers refuse simple changes (such as a navigation change from marketing) that would break 1000 tests.
- **The first rule of software design, for testability or any other reason: do not depend on volatile things.** GUIs are volatile, and suites that work through the GUI must be fragile. So design the system and tests so business rules can be tested without the GUI.
- The **testing API** is an API the tests use to verify all business rules. It is a superset of the interactors and interface adapters the UI uses, with superpowers: it can bypass security constraints, bypass expensive resources (such as databases), and force the system into specific testable states. Its purpose is to decouple the tests from the application: not only from the UI but from the application's structure.
- **Structural coupling** is one of the strongest and most insidious forms of test coupling. Example: a test class for every production class and a test method for every production method; every change to production methods or classes forces many test changes. The testing API hides the application's structure, so production code and tests can each be refactored without affecting the other. This matters because over time tests grow more concrete and specific while production code grows more abstract and general; structural coupling blocks that and keeps production code less general than it could be.
- The testing API's superpowers could be dangerous in production. If that is a concern, keep the testing API and the dangerous parts of its implementation in a separate, independently deployable component.
- Tests must be designed as part of the system to give stability and regression protection. Tests not designed that way tend to be fragile and hard to maintain and often end up discarded.

## 11 Clean embedded architecture

- Software does not wear out, but firmware and hardware become obsolete and force software changes. Software can be destroyed from within by unmanaged dependencies on firmware and hardware. Embedded software is commonly denied a long life by being infected with hardware dependencies. Embedded hardware keeps evolving while the software keeps growing in features and complexity.
- **Firmware** is not defined by where code is stored (ROM, EPROM, flash); those definitions are wrong or obsolete. Code is firmware because of what it depends on and how hard it is to change as hardware evolves. **Software**, by contrast, is code that can have a long useful life because it is not bound to particular hardware or firmware. Write less firmware and more software.
- Non-embedded developers write firmware too: whenever they bury SQL in code, spread platform dependencies through code, or (on Android) fail to separate business logic from the Android API. Examples: in a phone-system redesign, the legacy code was the only spec, and with no separation between the telephony technology and the call logic the whole product was firmware; a serial-port command dispatcher in the same file as the UART code is firmware instead of long-lived software.
- Three activities in building software (Kent Beck): (1) make it work, or you are out of business; (2) make it right: refactor so you and others can understand and evolve it; (3) make it fast: refactor for needed performance. Much embedded software is written only to work, often with an obsession with micro-optimizing for speed, so code that could be software becomes firmware. Most non-embedded apps are no different. "Plan to throw one away" (Brooks) is virtually the same advice: learn what works, then build a better solution.
- The **App-titude test** is merely getting an app to work. Programmers who care only about passing it do their products and employers a disservice. Example: a small embedded file that mixes business rules (computing RPM, averaging, sensor zeroing), hardware setup (interrupt handlers, sleep), button handling, A/D reading, and flash persistence, all in processor-specific extended C, testable only on the target; it works, but it cannot have a long life unless the hardware never changes.
- Embedded developers face limited memory, real-time deadlines, limited IO, unusual user interfaces, and real-world sensors; hardware is usually built concurrently with the software, so there may be nowhere to run code, and early hardware has defects. Embedded work is special, but not so special that clean architecture does not apply.
- The **target-hardware bottleneck**: embedded code built without clean architecture can often be tested only on the target hardware, which slows development. **A clean embedded architecture is a testable embedded architecture**, and it removes the bottleneck.
- Start with three layers: software, firmware, hardware. Hardware will change (obsolete parts, lower power, better performance, lower cost), so structure the system so the change is no bigger a job than necessary. The hardware/rest-of-system line is given once hardware exists, but nothing stops hardware knowledge from polluting all the code; without care about what modules may know, code becomes hard to change, not only for hardware changes but for user requests and bug fixes.
- Intermingled software and firmware is an anti-pattern: the code resists change, changes have unintended consequences, minor changes need full regression tests, and without automated tests you face manual testing and new bug reports. The software/firmware line is usually less clear than the code/hardware line; firming it up is part of the embedded developer's job.
- **HAL (hardware abstraction layer)**: the boundary between software and firmware. It exists for the software above it, and its API is tailored to that software's needs. Examples: firmware can store bytes in flash, but the application needs to store name/value pairs, so the HAL offers that without revealing whether it uses flash, disk, cloud, or memory; firmware might offer Led_TurnOn(5), but if the LED means low battery the HAL offers Indicate_LowBattery(), hiding the GPIO wiring. Do not reveal hardware details to the HAL's users. Software above a good HAL can be tested off the target hardware; the HAL provides the **seams** (substitution points) for that. Layers may contain layers: layering is a repeating fractal pattern, not a fixed set.
- Vendor tool chains add headers and C extensions (new keywords, pseudo-globals mapped to registers, IO ports, timers, interrupt controllers). Code using them looks like C but is not C and will not compile for another processor, maybe not even another compiler. Assume the vendor means to help, but limit which files may know about the extensions. Do not use vendor type headers (such as acmetypes.h) directly, because they tie code to one chip, give wrong integer sizes when testing off-target, and hinder porting; use standard stdint.h, and if the target compiler lacks it, write your own that maps standard types to the vendor's.
- All software should be processor independent; not all firmware can be, because some must use the chip's extensions to reach its peripherals. Use device registers directly in very few places, confined entirely to firmware; anything that knows the registers is bound to the silicon. A **PAL (processor abstraction layer)** inside firmware isolates processor-specific functions, so firmware above it can be tested off-target.
- In bare-metal systems a HAL may be enough. Systems using an RTOS or embedded Linux/Windows also need protection from the operating system. Treat the OS as a detail. Using an OS directly causes trouble if the supplier is bought and royalties rise or quality drops, or if needs outgrow it: lots of code must change, both for the new API and for the new OS's different primitives. An **OSAL (operating system abstraction layer)** isolates software from the OS; it may be as simple as renaming functions or may wrap several together. Order: software, OSAL, OS, HAL, firmware, hardware. With an OSAL, moving to a new OS means writing a new OSAL to a defined interface instead of modifying lots of complex code; the latter is preferred. The OSAL also isolates duplicated OS-usage code, need not add much overhead, and can encourage a common structure (for example, message passing instead of each thread handcrafting concurrency). A good OSAL provides seams for off-target, off-OS testing.
- Inside each layer, apply separation of concerns, programming to interfaces, and substitutability. Modules that interact through interfaces can swap providers (a custom target printf can replace the standard one if the interface matches), and each interface is a seam for off-target testing. Use header files as interface definitions, holding only function declarations and the constants and struct names they need; keep implementation-only data structures, constants, and typedefs out, because fewer places that know changeable details means fewer places to find and fix.
- Do not repeat conditional compilation to switch code per target. Once is fine; #ifdef BOARD_V2 six thousand times violates DRY. Instead hide the hardware type under a HAL and bind software to hardware through the linker or runtime binding.
- Letting all code become firmware and testing only on the target are bad for a product's long-term health; a clean embedded architecture is good for it.

## 12 Details

### 12.1 The database is a detail

- From an architectural view the **database** — the software utility that gives access to data — is a detail, like a doorknob in a house's architecture. It is a low-level mechanism, and a good architect does not let low-level mechanisms pollute the system architecture.
- **The database is not the data model.** The **data model** — the structure you give the data inside the application — is highly significant to the architecture. The technology that moves data on and off a disk is not. Relational databases (Codd, 1970; dominant by the mid-1980s) are elegant, disciplined, and robust, but a technology, however brilliant, is still a detail.
- Arranging data into rows in tables has no architectural significance; tables are merely convenient for some kinds of access. Use cases should neither know nor care about tabular structure. Knowledge of it belongs only in the lowest-level utility functions in the outer circles. Passing database rows and tables around the system as objects (as many data access frameworks allow) is an architectural error: it couples use cases, business rules, and sometimes the UI to the relational structure.
- Why databases dominate: for five decades data lived on rotating magnetic disks, and disks are slow. Reading a byte means moving the head, waiting for the sector, reading the whole sector (often 4K) into RAM, and indexing into it: milliseconds, a million times a processor cycle. Slow disks require indexes, caches, optimized queries, and a regular data representation, which split into two kinds of system:
  - **File systems** are document-based: good at storing and fetching whole documents by name, poor at searching content (easy to find login.c; slow to find every .c file containing a variable x).
  - **Database systems** are content-based: good at finding and relating records by shared content, poor at storing opaque documents.
- Disks are being replaced by RAM and will go the way of tape and floppies [the author's prediction]. If all data were in RAM, programmers would not organize it into tables or files; they would use linked lists, trees, hash tables, stacks, and queues. They already do: they read data from databases and files into RAM and reorganize it into those structures, and very rarely leave it as tables or files.
- So the database is a detail because it is just a mechanism to move data between disk and RAM, a big bucket of bits for long-term storage, and the data is seldom used in that form. Architecturally, do not care about the form of data on disk, or even acknowledge the disk exists.
- Performance is an architectural concern, but storage performance can be entirely encapsulated and separated from the business rules; moving data in and out quickly is a low-level concern for low-level access mechanisms.
- Example: a late-1980s network-management product stored its data in random-access files as trees and linked lists, because the data had few content-based relationships and that form was easiest to load into RAM. Marketing insisted on an RDBMS because customers expected one: a check-box item for buyers, irrational and external but real. The author was right on engineering grounds to keep it out of the architectural core, wrong to resist it entirely. The expectation came from vendors' marketing, which convinced executives that corporate "data assets" needed a database's protection. ("Enterprise" and "SOA" have more to do with marketing than reality, in the author's opinion.)
- When an external, non-technical demand forces a database in, bolt it on the side with a narrow, safe data access channel, and keep the preferred storage in the core. Market expectations can be real requirements; accommodate them without letting them corrupt the core.

### 12.2 The web is a detail

- The web changed nothing, or should not have. It is the latest swing in an oscillation, since the 1960s, between putting computing power in central servers and putting it at the terminals: punched cards, mainframes with smart terminals, minicomputers with dumb terminals, client-server; then, within the web era, server farms with dumb browsers, applets, dynamic server content, Ajax and whole applications in the browser, and JavaScript back on the server with Node. The swings will likely continue.
- Architects must look at the long term. Short-term swings such as where computing power lives must be pushed away from the core business rules.
- Decouple business rules from the UI in advance, because marketing-driven UI changes come without warning. Examples: a popular desktop finance app was remade to look like a browser; users hated it and it was reverted. A phone OS upgrade changed the look and feel of every app.
- The GUI is a detail, the web is a GUI, so the web is a detail. Put it behind a boundary. The web is an IO device, and the reason for device independence, known since the 1960s, applies unchanged.
- Objection: a rich web GUI (client-side validation, drag-and-drop, widgets) seems too rich for full device independence. True: the UI–application interaction is chatty and specific to the kind of GUI, so it cannot be abstracted the way UNIX abstracts devices. The resolution is to abstract a different boundary, the use-case boundary:
  1. Treat the business logic as a suite of use cases, each defined by input data, processing, and output data.
  2. Let the UI and the application dance until the input data is complete.
  3. Put the complete input into a data structure and execute the use case.
  4. Put the output into a data structure and feed it back into the UI dance.
  Each use case then operates the UI device independently of the device.
- This abstraction is not easy and will likely take several iterations, but it is possible and often very necessary.

### 12.3 Frameworks are details

- Frameworks are generally good (many are free, powerful, useful), but they are not architectures, though some try to be.
- Framework authors, however well-meaning, do not have your interests at heart; they solve their own problems and those of people they know. A framework is useful to the extent your problems overlap theirs, which is usually a lot.
- The relationship is extraordinarily asymmetric: you make a huge long-term commitment; the author makes none to you. You take all the risk. Framework documentation typically urges you to wrap your architecture around the framework, deriving from its base classes and importing it into your business objects. Coupling is no risk to the author, who controls the framework, and the author wants you coupled because it is then hard to leave.
- Risks:
  - Framework architecture is often not clean and violates the Dependency Rule, asking you to inherit its code into your Entities, the innermost circle; once in, it does not come out.
  - It may help early, but the product may outgrow it, and a tightly coupled framework fights you more and more.
  - It may evolve in unhelpful directions, forcing upgrades and removing or changing features you rely on.
  - A better framework may appear that you wish you could switch to.
- **Do not marry the framework.** Use it, but do not couple to it. Keep it at arm's length as a detail in an outer circle; keep it out of the inner circles. If it wants your business objects to derive from its base classes, refuse: derive proxies instead, and keep them in components that are plugins to the business rules. Example: with Spring, do not scatter @autowired through business objects; business objects should not know Spring. Use Spring to inject dependencies into Main, which may know Spring because it is the dirtiest, lowest-level component.
- Some frameworks you simply must marry, such as the C++ STL or Java's standard library. That is normal, but it should be a conscious decision, because marriage means being stuck with it for the life of the application.
- When facing a framework, do not marry it right away. "Date" it for a while, and keep it behind an architectural boundary as long as possible.

### 12.4 Case study: a video sales website

- Product: a site selling videos. Individuals pay one price to stream and a higher price to download and own; businesses buy streaming-only licenses in batches with quantity discounts. Individuals usually both buy and watch; in businesses, some people buy and others watch. Authors supply videos, descriptions, and ancillary files (exams, problems, solutions, source code). Administrators add series, add and remove videos, and set prices.
- Step 1: **identify the actors and use cases.** Actors are the primary sources of change (SRP): every new or changed feature serves one actor. So partition the system so a change for one actor affects no other. Here there are four actors: Author (submit video, exam, description), Admin (add series, publish video, remove video, set license price), Purchaser (buy download, streaming, or business license; view catalog as purchaser), Viewer (view catalog as viewer, stream video, download video). (The use case list is deliberately incomplete; there is no log-in or log-out.)
- An **abstract use case** sets a general policy that other use cases flesh out. Example: "View Catalog as Viewer" and "View Catalog as Purchaser" both inherit from abstract "View Catalog," as do the purchase use cases from "Purchase License." Abstract use cases are not strictly necessary, but when two use cases are very similar, it is wise to recognize the similarity and unify it early.
- Step 2: **build a preliminary component architecture.** Partition into views, presenters, interactors, and controllers separated by architectural boundaries, then split each category by actor (Admin, Author, Purchaser, Viewer). Abstract use cases get special components (Catalog View, Catalog Presenter) with abstract classes that the actor-specific views and presenters inherit. Below the boundary sit revenue gateways, data gateways, and the database. Each component is a potential jar or DLL.
- Break the build into fine-grained components so independent deliverables could be built, but reserve the right to combine them for deployment, so deployment can adapt as the system changes. Possible groupings: five jars (views, presenters, interactors, controllers, utilities); or views and presenters together with the rest separate; or, most primitively, two jars: views plus presenters, and everything else.
- Flow of control runs from controllers through interactors and presenters to views. Most dependency arrows point against that flow, because every dependency crosses a boundary toward the higher-level policy. Using relationships point with the flow of control; inheritance relationships point against it. This is the OCP: low-level changes do not ripple up to high-level policy.
- The architecture separates along two dimensions: by actor (SRP) and by level of policy (Dependency Rule). Both separate components that change for different reasons (actors) and at different rates (levels). With code structured along both, components can be grouped into deliverables in any sensible way, and the grouping is easy to change later.

### 12.5 Packaging code (guest view: Simon Brown)

This subsection is a guest author's view. It refines, and in places disagrees with, the rest of the distillate; disagreements are marked.

- Good advice about classes, components, boundaries, and dependencies is not enough. The devil is in the implementation details.
- Brown accepts the SOLID, REP, CCP, and CRP advice but, from a career of mostly layered Java enterprise systems, reaches a different conclusion about how to organize code.
- Running example: an online bookstore's "view orders" use case with OrdersController (web), OrdersService and OrdersServiceImpl (business logic), OrdersRepository and JdbcOrdersRepository (persistence). Applies beyond Java.
- Four ways to organize code:
  1. **Package by layer**: horizontal layers by technical role (web, business logic, persistence), typically one package each. In a **strict layered architecture** each layer depends only on the next lower layer, giving an acyclic graph with all arrows pointing down. It is a quick, simple start, but as the code grows three big buckets are not enough. It screams nothing about the domain: layered code bases from very different domains look alike.
  2. **Package by feature**: vertical slices by feature, domain concept, or aggregate root, with all types for a concept in one package named after it. It is a simple refactoring of package by layer, its top level screams the domain, and the code for a changed use case is in one place (less important with modern IDE navigation). Teams often move from layers to features; Brown considers both suboptimal.
  3. **Ports and Adapters** (Hexagonal Architecture, also boundaries/controllers/entities): an inside of domain code and an outside of infrastructure (UIs, databases, integrations). The outside depends on the inside, never the reverse. Name everything inside in the **ubiquitous domain language**: OrdersRepository becomes Orders, because the domain talks about orders, not repositories. (The diagram shown omits interactors and data-marshaling objects.)
  4. **Package by component** (Brown's recommendation; disagrees with the main text's choices): bundle all responsibilities of one coarse-grained component (business logic plus persistence) into one package, with a service-centric view, and keep the UI separate, treating the web as just another delivery mechanism. Code that needs orders has one place to go (OrdersComponent); inside, business logic and persistence are still separated, but that is hidden from consumers. It resembles a micro-service (an OrdersService owning everything about orders); the key difference is the decoupling mode. Well-defined components in a monolith can be a stepping stone to micro-services.
- **Definition conflict.** In the main text a component is a unit of deployment (a jar in Java). Brown defines a **C4 component** as a grouping of related functionality behind a nice clean interface, residing inside an execution environment such as an application; whether it is a separate jar is irrelevant. The **C4 model**: a software system contains one or more containers (web apps, mobile apps, standalone apps, databases, file systems); each container contains components; each component is implemented by classes. Outside this subsection, "component" always means the unit of deployment.
- Layering can be cheated while staying acyclic and downward. Example: a newcomer injects OrdersRepository straight into OrdersController, bypassing OrdersService; arrows still point down, but the architecture has degraded. Brown often sees this as a consultant, usually revealed when a team first visualizes its code. A **relaxed layered architecture** lets layers skip neighbors (a controller using repositories directly). Skipping is sometimes intended, as with CQRS (separate patterns for updating and reading data), but often undesirable, especially when the business layer enforces authorized access to individual records.
- A rule like "web controllers should never access repositories directly" is needed, but enforcement is the real question. "Discipline and code reviews because we trust our developers" fails when budgets and deadlines loom. Static analysis tools with build-breaking rules ("types in web must not access types in data") are crude but can work; both discipline and tooling are fallible and give slower feedback than necessary. Left unchecked, violations turn a code base into a **big ball of mud**. **Use the compiler to enforce the architecture if at all possible.**
- Developers overuse `public` by muscle memory. If every type is public, packages are only folders, not encapsulation, and nothing stops code from instantiating a concrete class directly. With everything public, the four styles are syntactically identical (same dependency arrows): four descriptions of a horizontally layered architecture. Java access modifiers are imperfect (package hierarchy exists only in names and directories, so access cannot follow it), but ignoring them is asking for trouble.
- What can be hidden in each style (types with inbound dependencies from other packages must be public; the rest can be package-protected):

  | Style | Public | Package-protected |
  |---|---|---|
  | Package by layer | OrdersService, OrdersRepository interfaces | implementations |
  | Package by feature | OrdersController only | everything else (so order data is reachable only through the controller, which may or may not be wanted) |
  | Ports and Adapters | OrdersService, Orders interfaces | implementations, injected at runtime |
  | Package by component | OrdersComponent interface only | everything else |

  The fewer public types, the fewer potential dependencies. In package by component, code outside the package cannot use OrdersRepository, so the compiler enforces the architecture (short of cheating with reflection, which you should not do). .NET can do this with `internal`, but it needs a separate assembly per component. This advice applies to monolithic applications in a single source tree.
- Module systems (OSGi, Java 9 modules), used properly, separate public types from published types: a module can make all types public but publish only a few for outside use.
- Another way to decouple: separate source trees (separate Maven, Gradle, or MSBuild modules). For Ports and Adapters: (1) domain code independent of technology (OrdersService, OrdersServiceImpl, Orders); (2) web (OrdersController); (3) persistence (JdbcOrdersRepository). The last two depend at compile time on the domain tree, which knows nothing of them. A tree per component is ideal but idealistic; it has real performance, complexity, and maintenance costs. A simpler split is two trees, domain (inside) and infrastructure (outside), with infrastructure depending on domain; it works but risks the **Périphérique anti-pattern**: with all infrastructure in one tree, infrastructure in one area (a web controller) can call infrastructure in another (a repository) directly, bypassing the domain, like a ring road around a city, especially if access modifiers are not used.
- Best design intentions can be destroyed in a flash if the implementation strategy is ignored: decide how the design maps to code structures, how code is organized, and which decoupling modes apply at runtime and compile time. Leave options open where it helps, but be pragmatic about team size, skill, solution complexity, time, and budget; use the compiler to enforce the chosen style; and watch for coupling elsewhere, such as in data models.

## 13 Judgment: lessons, tradeoffs, and failure modes

### 13.1 Boundary direction in practice

- A boundary is **dependency normal** when source code dependencies point the same way as the flow of control, and **dependency inverted** when control flows across it opposite to the source code dependency. Examples from an early overlay system with no OS: applications sent output strings to a supervisor that buffered them for slow terminals, and the applications had source code dependencies on the supervisor (dependency normal); this boundary kept applications ignorant of the output device. The supervisor also started applications without any source code dependency on them, because every application was entered by jumping to the same address in the overlay area, which acted as a polymorphic interface (dependency inverted).
- Soft, poorly enforced boundaries leave couplings everywhere. Example (typical of early-1970s software): a utility layer called the master operating program, which had been modified for that layer and called back into it, so they were not really separate layers. A domain-specific language run by an isolation layer does not by itself make applications machine-independent: that one only gave programmers a simpler language than assembler, and its quirks were deeply coupled to the layers beneath.
- A boundary across which only very short, simple command packets pass (a primitive language such as "DIAL XXXX" or "MEASURE") can be very clean and highly decoupled. Example: moving report analysis and printing from remote line testers to a central computer, leaving only dialing and measurement in the testers, made screens much faster (reports no longer trickled over slow modems) and shrank the testers' expensive memory.
- Missed boundaries are expensive. Example: line testers did dialing and measurement in one device, but digital switching needed measurement at the distribution points and dialing at the central office; recognizing that obvious boundary years earlier would have saved a fortune.
- The direction of dependencies, not the deployment mechanism, decides whether a design follows the Dependency Rule. Statically linked code can have a plugin architecture. Example: in one statically linked C++ product, GUI screens were plugins to a framework holding all high-level GUI policy, while for scoring the reverse held: the high-level scoring policy lived in each screen and the scoring framework plugged into it. Both followed the Dependency Rule.
- Layers whose dependencies follow the flow of control instead of pointing toward policy are not enough. Example: a modeling tool built in strictly enforced layers (GUI → representation → manipulation rules → database) was releasable and independently deployable, but had no true plugin architecture, and its failure to point dependencies toward policy helped kill it.
- An architecture can have true boundaries without being a clean plugin architecture. Example: an early voice-mail system was, in today's terms, service-oriented: a listener per phone line started a handler process per call; as the call changed state, the running service wrote its state to disk, started the next service, and exited. The services were independently deployable, each owned a domain of responsibility, and many dependencies ran the right way.

### 13.2 Plugins, polymorphism, and data-driven flow

- Calling through a table of function pointers loaded at run time is polymorphic dispatch, the essence of objects, and yields a literal plugin architecture.
- When a program is linked as one binary at absolute addresses, adding or removing any code shifts every later address, so even a trivial change affects the whole deployed image. Example: a 30K firmware image spread over 30 EPROM chips meant every change replaced all 30 chips in the field, with mislabeled chips, wrong swaps, and broken pins.
- Procedure that made those chips independently deployable ("vectorization"):
  1. Split the program into independently compilable source files, each fitting one chip and told its own load address.
  2. Start each file with a fixed-size table of the addresses of all its subroutines (40 bytes, so at most 20 subroutines per chip).
  3. Reserve a RAM area of vectors, one table per chip.
  4. Make every subroutine call an indirect call through the RAM vector.
  5. At boot, copy each chip's table into its RAM vector, then jump to the main program.
  After this, a fix or feature meant shipping only one or two chips. Extended further, a feature could be installed by plugging its chip into an open socket, after which its menu appeared and it bound into the application automatically. A mutable vector table also allows field patching: point a faulty routine's vector at empty RAM and type in the fixed routine, deferring the new chip to a routine visit.
- Externalizing the application's flow into a data-driven state machine (each call state transition starting the next service, the state machine read from a text file) lets you change the flow without changing code (OCP), add a service and wire it in by editing the file, and even do so while running (hot swapping).
- Data shared between processes in separate memory partitions cannot contain pointers, because a pointer into one partition means nothing in another. So such a store can hold only strings and constants; tree data must be serialized to strings (one 1985 format did what XML or JSON do today). There is nothing new under the sun: micro-services talking through shared-memory sockets with an XML analog existed in 1985.
- A nonpreemptive task switcher can work by having a task call block(eventCheckFunction), which suspends it and adds the function to a polling list; the scheduler polls until a function returns true and then runs that task.

### 13.3 Hardware, vendors, and third parties

- Isolate hardware from the business rules, and abstract the interfaces to devices. If device control code is scattered at the bit level through business rules and UI, changing or adding a device type touches hundreds of places or forces a hack. Example: a new in-house modem with an entirely different control structure had to coexist with old ones; the team changed the low-level serial-bus write routine to recognize old-modem bit patterns and translate them into new-modem commands, the worst hack imaginable. Do not count on hardware designers keeping a device's software interface unchanged; the team begged, and the new modem came back entirely different.
- Databases are details that should be isolated from the system's business purpose. Example: embedded SQL and vendor-specific database API calls were spread through a C code base; when the vendor discontinued the database, three months of trying to switch vendors were abandoned as hopeless, and the company paid a third party rising yearly fees to keep the dead database alive. Avoid strongly coupling a system to third-party software, because the vendor or product can disappear and strand you.
- A big, slow, intrusive, expensive third-party framework (an object-oriented database meant to make stored objects look like RAM) can impede progress at nearly every level.

### 13.4 Code quality and its economics

- Code no one can understand becomes impossible to change safely, and it does the most damage when it sits under the system's main economic value. Example: dispatch logic written by a brilliant, uncommunicative developer who then left broke on every change until management ordered it locked and never modified: officially rigid. This is the value of clean code.
- Skipping architecture in the rush to code ("We didn't have time for architecture. Just code") produced goo such as a 3000-line C function, and the company failed to sell after three years.

### 13.5 Process traps

- **Grand redesign.** A redesign running alongside a live system rarely catches up: a redesign team can hardly overtake a large staff that keeps changing the old system (for example, absorbing new regional requirements). One rewrite lost its first team entirely after two or three man-years; the restart took years and may never have been deployed.
- **Forks.** Forking a shared code base forces changes to be passed around and merged by hand. Forking to handle regional variations makes fixes hard to apply across forks and reintegration very hard; three attempts to merge such forks back, turning differences into configuration, all failed because the modules had diverged and the market kept moving.
- **The schedule trap.** Repeatedly postponing a necessary architectural development because the customer's deadline seems far away leaves no time when it suddenly arrives. In one case the team then shipped a narrowly scoped stopgap built in about a week.
- **Over-architecture.** Many more layers than needed, each with its own communication overhead, significantly reduce productivity. One product built that way was scrapped after many man-years and two tepid releases and replaced by a small team's little application. Architecture must adapt to the size of the problem; architecting for the enterprise when you need a small desktop tool is a recipe for failure.
- **Premature reuse.** The early OO promise that clean OO code would naturally yield reusable code was false. A framework built for one application alone is not reusable: one 45,000-line framework built over a year with its first, most complex application fit later applications poorly because of subtle frictions. **You cannot make a reusable framework until you have made a usable one; build reusable frameworks together with several reusing applications.** That team rebuilt the framework while writing four applications at once, reworking code until it fit all four without modification; it delayed the project nearly a year, after which new applications came every few weeks and dates were met.
- **Different shapes can both work.** Two multiplexing boards, one built as a dataflow of small tasks linked by queues (like pipes and filters) and the other as one large task per terminal doing the whole job, both worked well. Architectures can be wildly different yet equally effective.

### 13.6 Priority rules where principles pull against each other

- **Structure versus behavior.** Structure (ease of change) wins over current behavior because a changeable program can be made to work, and an unchangeable one dies with the next requirement (§1.4). Developers must fight for it because managers cannot judge it.
- **Duplication versus decoupling.** Remove true duplication; keep accidental duplication, because unifying code that changes for different reasons couples its actors (§3.2, §5.5).
- **Reuse versus developability (REP/CCP versus CRP).** Early in a project, CCP outweighs REP; move toward REP as other projects come to depend on the code (§4.3).
- **Stability versus flexibility.** Make stable components abstract so they can be extended; keep volatile code concrete and unstable (§4.7).
- **Full boundary versus YAGNI.** Over-engineering is often worse than under-engineering, but missing boundaries are costly to add. Guess intelligently, use partial boundaries as placeholders when warranted, watch for friction, and implement the boundary when its cost drops below the cost of ignoring it (§9.2, §9.3).
- **Operation versus development.** Operational problems can usually be bought off with hardware; development, deployment, and maintenance problems cost people, so they weigh more (§5.2).
- **Services versus monolith.** Start at source-level decoupling with components kept separable; promote to deployment units or services only when development, deployment, or operational pressure demands, and be able to go back (§5.6, §10.2).
- **Ideal versus external demand.** When customers or the market demand a technology without engineering reason, accommodate it at the side of the system through a narrow channel, keeping it out of the core (§12.1).

## 14 Scope and limits

- The rules apply to every kind of software system — embedded, batch, real-time, web, GUI, database, games — because all code is built of the same few elements (§1.1). They apply in any language and paradigm; "class" means any grouping of functions and data (§3.1).
- The SOLID principles act at the module level; the component principles at the level of deployable components; the boundary and policy rules at the system level. Each level needs its own principles; success at one does not guarantee success at the next (§3.1).
- Several effects depend on language type. Recompilation and redeployment caused by declarations (ISP, abstract components, Facade recompiles) are effects of static typing; dynamically typed languages avoid them (§3.5, §4.6, §9.2).
- The DIP is not absolute: depending on stable concrete platform facilities is fine; only volatile concretions are targets (§3.6). Some frameworks (standard libraries) must be married, consciously (§12.3).
- A small single team early in development may find architectural structure an impediment; a monolith without components can work for it (§5.2). A trivially small program would not get a clean architecture at all (§9.3).
- Full immutability needs unbounded storage and speed; in practice it needs compromises (§2.4). An atom-style compare-and-swap does not protect several dependent variables (§2.4).
- The component metrics (I, A, D) measure conformance to an arbitrary standard; they are aids, not truths (§4.7).
- The Dependency Rule never relaxes, but the number of circles is not fixed (§8.2).
- The packaging advice in §12.5 (compiler enforcement through access modifiers) applies to monolithic applications in one source tree.
- Not covered: how to build any specific framework, database, or UI; formal proofs of correctness (abandoned, §2.2); detailed treatments of SOLID beyond their architectural consequences.

## 15 Operating rules

1. Measure a design by the effort needed to meet needs over the system's life; rising effort per release means bad design (§1.2).
2. Never trade structure for speed: messes are slower at every time scale (§1.3).
3. Defend architecture against urgent but unimportant features; it is the developers' job (§1.4).
4. Point every source code dependency toward higher-level policy; invert with an interface where control flows the other way (§2.3, §3.6, §8.3).
5. Give each module one actor; separate code that different actors depend on (§3.2).
6. Add behavior by adding code; protect higher-level components from changes in lower-level ones (§3.3).
7. Keep implementations substitutable; never special-case one implementation by name (§3.4).
8. Do not depend on anything you do not use, whether methods, classes, or components (§3.5, §4.2).
9. Never mention the name of anything concrete and volatile; create volatile objects through factories, gathered in Main (§3.6, §10.1).
10. Group classes into components by common reason and time of change; split classes not used together (§4.2).
11. Allow no cycles between components; break any cycle with an interface or a new component (§4.4).
12. Depend in the direction of stability (decreasing I); make stable components abstract (§4.6, §4.7).
13. Keep components near the Main Sequence; investigate any D far from 0 (§4.7).
14. Separate policy from details; keep the policy ignorant of databases, web, frameworks, devices, and delivery (§5.3).
15. Maximize the number of decisions not made; treat already-made tool decisions as if they were still open (§5.3).
16. Split along both axes: horizontal layers by reason for change and vertical use cases (§5.4).
17. Before merging similar code, confirm the duplication is true; give the UI its own view model (§5.5).
18. Keep the decoupling mode open; start with source-level decoupling and promote only under pressure (§5.6).
19. Draw boundaries along every axis of change; make the less relevant side depend on the more relevant side (§6.2, §6.3).
20. Let higher-level processes and services contain no names, addresses, or URIs of lower-level ones (§6.4).
21. Keep Entities pure business; keep use cases free of HTML, SQL, and delivery knowledge (§7.2).
22. Use plain, independent request and response models; do not put Entities or database rows in them (§7.2, §8.3).
23. Make the top-level structure scream the domain and use cases, not the framework (§7.3).
24. Cross boundaries with simple data structures shaped for the inner circle (§8.3).
25. Put hard-to-test behavior in humble objects at the edge; keep SQL only in gateway implementations (§9.1).
26. Use partial boundaries as cheap placeholders and watch them for decay (§9.2).
27. Implement a boundary when the cost of ignoring it exceeds the cost of building it; reevaluate continually (§9.3).
28. Run architectural boundaries through services, not between them (§10.2).
29. Test business rules through a testing API, not the GUI; do not couple tests to code structure (§10.3).
30. In embedded code, hide hardware behind a HAL and the OS behind an OSAL so the code can be tested off target (§11).
31. Use frameworks without marrying them; keep them in the outer circle and confine framework injection to Main (§12.3).
32. Enforce the architecture with the compiler where possible; minimize public types (§12.5).
33. Build reusable frameworks only alongside several applications that use them (§13.5).
